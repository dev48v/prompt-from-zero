PromptFromZero · Day 62

🧭 Algorithm of Thoughts (AoT) — Sel et al., 2023. Tree-of-Thoughts works, and it works by externalising the search: one call to propose the next steps, another call per candidate to score it, prune, repeat — so a single Game-of-24 hand costs you hundreds of API round-trips. AoT asks a blunter question: if the model can imitate a worked example, why not show it the whole search — including the branches that failed and the explicit act of backtracking — and let it run the search inside one generation? The exemplar stops being a solution and becomes a search transcript. This page computes that difference rather than asserting it: an exhaustive Game-of-24 solver in exact rational arithmetic (because 8/(3-8/3) is exactly 24 and in floats it is not), a real beam search with every generated and evaluated node counted, a real trajectory serialiser, a hand-written tokenizer measuring the actual prompt bytes on both sides, and a live crossover against a context budget you choose. It simulates the search, never the LLM — the paper's measured accuracy numbers are cited separately and never mixed into the live figures.

ToT pays for search in API calls. AoT pays for it in context.

🔨 Build it yourself

    
Algorithm of Thoughts is not a phrase you paste at the top of a prompt. It is a pipeline you write in your own code: an exact model of the problem, a real search over it, an instrumented count of what that search would cost through an API, and a serialiser that turns one run of that search — including its failures — into a single in-context exemplar. Below is exactly what this page runs, in the order you would write it. Every step is testable without an LLM, which is the point: you should know your ground truth long before you spend a token.

    
    

      
  1. 
        
    1
    Exact arithmetic first. Floats will lie to you about your own ground truth.
    
        
    Game of 24 looks like it lives in integers, and it does not: the moment a division lands on a non-terminating value, a double-precision solver starts giving wrong answers about which hands are solvable. The canonical case is 3 3 8 8, whose only solution is 8/(3-8/3). Evaluate it in doubles and you do not get 24 — you get 24 plus a few ulps, so a strict equality test rejects a correct solution, and a tolerance test invites false positives from the other direction. Build a two-integer rational with gcd reduction, do every operation on it, and compare numerator and denominator. It is fifteen lines and it removes an entire class of “my solver disagrees with the internet” bugs. The LOOK tab evaluates every complete expression both ways and prints how many correct solutions the float version throws away for the hand you picked.
    
        
    // STEP 1 - exact rationals. Everything downstream depends on this.
function gcdInt(a, b){ a = a < 0 ? -a : a; b = b < 0 ? -b : b;
  while (b){ const t = a % b; a = b; b = t; } return a; }

function rat(n, d){
  if (d === 0) return null;                 // caller must handle
  if (d < 0){ n = -n; d = -d; }             // sign lives in the numerator
  const g = gcdInt(n, d); if (g > 1){ n /= g; d /= g; }
  if (n === 0) d = 1;                       // one canonical zero
  return { n: n, d: d };
}
const rAdd = (a,b) => rat(a.n*b.d + b.n*a.d, a.d*b.d);
const rDiv = (a,b) => b.n === 0 ? null : rat(a.n*b.d, a.d*b.n);
const rEq  = (a,b) => a.n === b.n && a.d === b.d;   // never ===, never epsilon

  2. 
        
    2
    Write the exhaustive solver before you write the prompt
    
        
    You cannot evaluate a search strategy without knowing the answer. For Game of 24 the whole space is small enough to enumerate: repeatedly pick two of the remaining values, apply one of the four operators in both operand orders, and recurse until one value remains. A few thousand complete expressions per hand, milliseconds of work. Once you have this, every later claim on the page becomes checkable — did the beam keep a branch that actually leads to 24, did the bounded depth-first walk miss a solution that exists, is this hand solvable at all. Skip it and you end up grading a model against your own guesses.
    
        
    // STEP 2 - enumerate every complete expression tree over the 4 cards.
function enumerateAll(cards, visit){
  const start = cards.map(c => ({ v: rat(c,1), ast: { t:"num", v:c } }));
  (function rec(list){
    if (list.length === 1){ visit(list[0]); return; }
    for (let i = 0; i < list.length; i++)
      for (let j = i + 1; j < list.length; j++){
        const rest = list.filter((_, k) => k !== i && k !== j);
        for (const cand of moves(list[i], list[j]))   // 6 ordered moves
          if (cand) rec(rest.concat([cand]));
      }
  })(start);
}
// 4 cards -> ~7,000 complete expressions. Instant. Do it.

  3. 
        
    3
    Canonicalize, or your “solution count” is meaningless
    
        
    Raw enumeration reports 3+8 and 8+3 as two findings, and with four cards that inflates a count by an order of magnitude. Define the equivalence you actually mean, then implement it: flatten runs of the same commutative operator, sort the children by their own canonical keys, and leave the non-commutative operators alone. State the equivalence on screen — this page counts solutions modulo commutativity and associativity of + and *, which means (a-b)+c and (a+c)-b are still counted separately even though they are numerically equal. A count you cannot define is a number you cannot defend.
    
        
    // STEP 3 - canonical key. Same key must imply same value, always.
function canonicalize(ast){
  if (ast.t === "num") return String(ast.v);
  if (ast.op === "+" || ast.op === "*"){
    const parts = [];
    (function flat(n){                       // flatten a+b+c, a*b*c
      if (n.t === "op" && n.op === ast.op){ flat(n.l); flat(n.r); }
      else parts.push(canonicalize(n));
    })(ast);
    parts.sort();                            // commutativity collapses here
    return "(" + ast.op + " " + parts.join(" ") + ")";
  }
  return "(" + ast.op + " " + canonicalize(ast.l) + " " + canonicalize(ast.r) + ")";
}
// Note the space separator: it stops "1 23" and "12 3" colliding.

  4. 
        
    4
    Build the ToT baseline and instrument the call counter from line one
    
        
    The reason to write the Tree-of-Thoughts baseline is not to beat it, it is to price it. Implement the standard loop — expand the frontier, score every candidate, keep the top b — but wrap it in counters that map onto real API traffic: one propose call per expanded state, one value call per candidate per vote. Do not estimate this. On this page, moving the beam slider from 1 to 10 changes the counted call total by roughly an order of magnitude, and it does so because the counter is attached to the actual loop rather than to a formula somebody wrote in a slide. The counter is what makes the AoT comparison a measurement instead of a slogan.
    
        
    // STEP 4 - the ToT loop, with the meter attached.
let generated = 0, evaluated = 0, expanded = 0;
let frontier = [rootState];
for (let depth = 0; depth < 3; depth++){
  const cand = [];
  for (const s of frontier){
    expanded++;                              // 1 propose call
    const ex = expandState(s);               // 6 moves per unordered pair
    generated += ex.generated;               // counted BEFORE validity
    for (const c of ex.children) cand.push(c);
  }
  for (const c of cand){ c.score = scoreState(c.vals); evaluated++; }
  cand.sort((x,y) => y.score - x.score || (x.key < y.key ? -1 : 1));
  frontier = cand.slice(0, beam);
}
const llmCalls = expanded + evaluated * votesPerCandidate;
    
      
    5. 

      
  5. 
        
    5
    Give the search an evaluator that is honestly imperfect
    
        
    This is the step that decides whether your page teaches anything. If you score states with a perfect oracle — “is 24 still reachable from here” — the search never takes a wrong turn, the transcript has no dead ends, and the AoT exemplar you serialise out of it demonstrates nothing except a lucky straight line. That is precisely the exemplar that teaches a model to guess. So model the LLM value prompt for what it is: exact where the arithmetic is trivial, a magnitude heuristic where it is not. Then flip between oracle and heuristic and watch the dead-end count in the transcript go from zero to something. The strictness control on this page exists to make that failure visible, not to hide it.
    
        
    // STEP 5 - a cheap scorer that gets things wrong, like the real one does.
function scoreState(vals, mode){
  if (mode === "oracle")  return reachesTarget(vals, 24) ? 1 : 0;
  if (mode === "none")    return 0.5;             // no evaluator at all
  if (vals.length <= 2)   return reachesTarget(vals, 24) ? 1 : 0;  // trivial
  // magnitude proxy: how near do the sum and the product land to 24?
  const s = vals.reduce(rAdd), p = vals.reduce(rMul);
  const best = Math.min(Math.abs(rNum(s) - 24), Math.abs(rNum(p) - 24));
  const divisors = vals.filter(v => { const q = rDiv(rat(24,1), v);
                                      return q && q.d === 1; }).length;
  return Math.min(1, 1 / (1 + best) + divisors * 0.08);
}
    
      
    6. 

      
  6. 
        
    6
    Run a bounded depth-first search and record every event
    
        
    AoT does not demonstrate an exhaustive search — an exhaustive Game-of-24 search is thousands of nodes and would not fit in anybody's context window. It demonstrates a search with a small branching limit, run to completion, so the transcript is a complete record of a deliberately narrow walk. That distinction matters twice over: it is what keeps the prompt finite, and it is what makes the demonstrated behaviour honest, because the model is being shown a procedure it can actually reproduce. Record structured events rather than strings — try, dead, backtrack, exhausted, solved — so you can re-serialise the same run at three verbosity levels without re-running it.
    
        
    // STEP 6 - bounded DFS. The trace is data, not text.
function aotSearch(root, branch, mode){
  const trace = []; let visited = 0, deadEnds = 0, found = null;
  (function dfs(st, depth){
    visited++;
    if (st.vals.length === 1){
      const win = rEq(st.vals[0], rat(24,1));
      trace.push({ k: win ? "solve" : "dead", depth: depth, st: st });
      if (!win) deadEnds++; else found = st;
      return win;
    }
    const kids = rank(expandState(st).children, mode).slice(0, branch);
    for (const kid of kids){
      trace.push({ k:"try", depth: depth, move: kid.move, st: kid });
      if (dfs(kid, depth + 1)) return true;
      trace.push({ k:"back", depth: depth, move: kid.move });   // the lesson
    }
    trace.push({ k:"exhausted", depth: depth, st: st });
    return false;
  })(root, 0);
  return { trace: trace, visited: visited, deadEnds: deadEnds, found: found };
}

  7. 
        
    7
    Serialise the trace — and keep the backtracks, they are the payload
    
        
    Now turn the event list into the exemplar. Indent by depth so the tree structure is visible in the token stream, print the exact value of every move so the model has arithmetic to imitate rather than invent, mark dead ends with a reason, and give backtracking its own literal line. That last part is the one people delete because it looks like noise, and deleting it is how you turn AoT back into ordinary few-shot prompting. The contrast panel on this page renders both versions of the same run side by side with their token costs: the pruned one is genuinely cheaper and it demonstrates a completely different behaviour — a confident answer with no procedure behind it.
    
        
    # STEP 7 - what the serialiser emits (normal verbosity, branch = 3):
[3 3 8 8]
  try 8 / 3 = 8/3          -> [3 8 8/3]
    try 3 - 8/3 = 1/3      -> [8 1/3]
      8 / (1/3) = 24       SOLVED
Answer: 8/(3-8/3) = 24

# and the same run with the failures deleted:
[3 3 8 8] -> [3 8 8/3] -> [8 1/3] -> 24
Answer: 8/(3-8/3) = 24
# cheaper, and it teaches the model to produce an answer, not to search.

  8. 
        
    8
    Find your context crossover before you ship, not after
    
        
    AoT's cost is a single prompt, and single prompts have a ceiling. The variables that push you into it are the branching limit, the verbosity, and the number of exemplar trajectories — and they interact, so intuition is useless here. Sweep them, tokenize the real string, and find the first configuration that exceeds the budget you actually have. On this page that sweep is live: raise the branching limit to 6 and set verbosity to full and watch the crossover marker walk left until a single exemplar no longer fits in 2,000 tokens. Measure with the tokenizer your provider actually uses before you commit; the one on this page is a documented approximation and says so.
    
        
    // STEP 8 - sweep the exemplar count until the budget breaks.
function sweepExemplars(hands, branch, mode, verbosity, budget){
  let cum = 0, crossover = null; const pts = [];
  hands.forEach((hand, i) => {
    const run  = aotSearch(rootFor(hand), branch, mode);
    cum += countTokens(aotTrajectory(run, verbosity, hand));
    pts.push({ k: i + 1, tokens: cum });
    if (crossover === null && cum > budget) crossover = i + 1;
  });
  return { points: pts, crossover: crossover };   // null = never crossed
}
// Report "no crossover within N" honestly. Do not extrapolate a curve
// you did not measure.

  9. 
        
    9
    Parse the model's answer yourself. The transcript is a story; only the parser is evidence.
    
        
    In-context search means the model narrates a search it may not have actually performed correctly, and a fluent transcript with a wrong final line is the most expensive failure mode there is, because it looks right. So do not grade on the narration. Take the final expression, parse it with a real precedence parser, evaluate it in the same exact rationals, assert it equals 24, and assert the multiset of leaf numbers is exactly the hand you dealt — models reuse a card or invent one far more often than they get the arithmetic wrong. This check is twenty lines, it runs offline, and it converts “the output looked plausible” into a hard pass or fail you can put in an eval suite.
    
        
    // STEP 9 - the only thing that counts as evidence.
function validate(answer, hand){
  const ast = parseExpr(answer);              // precedence parser, your own
  const val = evalExpr(ast);                  // exact rationals, step 1
  if (!val || !rEq(val, rat(24,1)))
    return { ok:false, why:"value is " + (val ? rStr(val) : "undefined") };
  const leaves = leafValues(ast).slice().sort((a,b) => a - b);
  const dealt  = hand.slice().sort((a,b) => a - b);
  if (leaves.join(",") !== dealt.join(","))
    return { ok:false, why:"used " + leaves.join(" ") + ", dealt " + dealt.join(" ") };
  return { ok:true };
}

// where you find out WHICH step of the demonstrated algorithm it dropped.

🎉 Day 62 of PromptFromZero done.
You learned Algorithm of Thoughts — Sel et al., 2023 — which starts from an uncomfortable fact about Tree-of-Thoughts: ToT's search is real, but it lives outside the model, so every node you generate and every node you evaluate is another API round-trip, and one hand of Game of 24 turns into hundreds of calls. AoT moves the search back inside the model by changing what the exemplar is. Instead of a worked solution, you show a worked search transcript — the branches you tried, the values they produced, the moment a branch went dead, and the literal act of backtracking — and the model imitates the algorithm rather than the answer, in a single generation. On this page nothing was asserted: an exhaustive solver in exact rational arithmetic gave ground truth (and showed you how many correct solutions a float-based solver silently discards), a real beam search counted every generated and evaluated node so the call total came from the loop rather than a formula, a real serialiser emitted the actual prompt text, and a hand-written tokenizer measured both sides and found the context crossover live. The two traps are both visible from the controls: switch the evaluator to oracle and the transcript loses its dead ends entirely, which is exactly the exemplar that teaches guessing rather than searching — and push the branching limit and verbosity up and the single AoT prompt walks straight through your context budget, because AoT does not delete the cost of search, it relocates it from calls into tokens. Trade calls for context deliberately, and measure the trade on your own problem. 👉 Next up — self-consistency over trajectories: when one in-context search is not enough, sample several and let them vote.
