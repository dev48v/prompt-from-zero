PromptFromZero · Day 59

✍️ Assistant Prefill (response priming) — a chat request isn't a question, it's a transcript: system turn, user turn, then an empty assistant turn the model fills in. Prefill means you write the first few characters of that assistant turn yourself, and the model — which cannot tell your text from its own — simply continues it. That one move settles the fight over output format by fiat instead of by request: an empty turn's most likely opening is “Sure! Here's the JSON you asked for:” followed by a markdown fence and a friendly sign-off, all of which breaks JSON.parse; a turn that already starts with { has no room for “Sure!” at all, because the only sensible continuation of an open brace is a JSON key. Land the prefill mid-string and the very next token is that string's contents. This page is genuinely interactive with no API and no network: a deterministic token-by-token decoder whose every step is chosen by really scanning the text written so far — brace depth, open strings, which schema keys already appear, whether a fence is open — so editing the prefill genuinely changes the decode path, plus real validators (JSON.parse, exact-label match, bullet-line parsing, SQL shape) scoring 14 checks across 4 tasks: baseline 4/14 · prefill 14/14. You also get a live stop sequence field, because prefill controls how a turn starts and a stop sequence controls where it ends. One honest caveat up front, covered in step 11: current Claude models reject a trailing assistant turn with a 400 — the affordance moved to output_config.format (structured outputs). The mechanism is still worth knowing cold: it's native anywhere you control the raw prompt, and it's the clearest way to understand why the first token owns the whole response.

Stop asking for the format. Start the reply yourself and the model has nowhere else to go.

Everything below is deterministic (no API key, no network). A tiny continuation decoder emits the assistant turn token by token; at every step it picks the next token by really scanning what's written so far — is the text empty, is a markdown fence open, is a JSON string unterminated, which schema keys are already present. So the prefill isn't a lookup key: it puts the decoder in a different state, and the decode path genuinely changes. Pick a task, edit the prefill, change the stop sequence, and watch the raw output and its checks recompute.

🔑 Prefill fixes the envelope, not the answer. Look at the checks: in every task the baseline already knew the right content — the order ID, the sentiment, the three risks, the query — and still failed, because it wrapped that content in a greeting, a markdown fence and a friendly sign-off. Format was the whole failure. Asking for the format in words is a request the sampler can ignore; prefilling it is a fact about the transcript — after {"order_id": " there is no continuation in which the model says “Sure!”, because the only thing that follows an unterminated JSON string is its contents. That's why a one-character prefill routinely beats three paragraphs of formatting instructions: the entire argument about output shape is really an argument about the first token, and prefill wins it before generation starts. Two things travel with it — a stop sequence so the turn also ends where you want (clear the stop field on the classification task and watch the exact-match check break), and the reminder that most APIs return only the generated text, so the prefill you sent must be concatenated back on before you parse.

Assistant prefill = write the opening of the model's own turn → it continues rather than restarts → the format is decided, not requested. Pair with a stop sequence; re-attach the prefill before parsing.

🔨 Build it yourself

    
Prefill is the smallest technique in this whole series — it is one extra message in the array — but everything around it is where the engineering lives: choosing a prefix that can only be continued one way, pairing it with a stop sequence, re-attaching the prefill before you parse, keeping the string developer-owned, and knowing which replacement to reach for on a model that no longer accepts a trailing assistant turn. Below is the exact deterministic harness this page runs — the state scans, the continuation decoder, the validators — followed by the production shape both ways: prefill where it's supported, and structured outputs where it isn't.

    
    
      
  1. 
        
    1
    The idea in one line — write the opening of the model's turn
    
        
    A chat call is a transcript the model completes. Normally you hand it an empty assistant turn and it writes the whole thing, greeting and all. Prefill hands it a turn that already starts — and because the model cannot tell your characters from its own, it finishes your sentence instead of starting its own.
    
        
    // Normal:   [system, user]                  -> model writes the WHOLE assistant turn
//           "Sure! Here's the JSON:\n```json\n{...}\n```\nLet me know!"
//
// Prefill:  [system, user, assistant:'{"']  -> model CONTINUES your text
//           'order_id": "A-1042", ... }'
//
// Same model, same prompt. The only change is where the turn starts.
    
      
    2. 
      
  2. 
        
    2
    Where it goes — a trailing assistant message
    
        
    There is no prefill parameter. You append one more message with role assistant as the last entry in the array. Assistant messages elsewhere in the conversation are ordinary history (that's how few-shot examples work) — only a trailing one is a prefill, because only the last turn is the one being generated.
    
        
    // STEP 2 — a prefill is just the last message, with role "assistant".
const messages = [
  { role: "user", content: 'Extract order_id, customer, total, status as JSON.\n\n' + doc },
  { role: "assistant", content: '{\n  "order_id": "' }   // <-- the prefill
];

// Mid-array assistant turns are NOT prefills — they are conversation history:
//   [user, assistant, user, assistant, user]            = few-shot / chat history
//   [user, assistant, user, assistant]                  = the last one is a prefill
    
      
    3. 
      
  3. 
        
    3
    Pick the shortest prefix that can only be continued one way
    
        
    A good prefill is not a sentence — it is the smallest string that makes exactly one kind of continuation plausible. One character is often enough. Anything longer than the format marker starts asserting content, which is a different and riskier thing (step 7).
    
        
    // STEP 3 — the prefills this page ships with.
const PREFILLS = {
  json:     '{\n  "order_id": "',   // lands mid-string: next token IS the value
  label:    'Label:',               // classification slot, one word follows
  bullets:  '-',                    // a bullet list can only continue as bullets
  sql:      'SELECT',               // SQL, not prose about SQL
  xml:      '<answer>',              // tag-delimited output for easy extraction
  letter:   'Dear Ms Alvarez,'      // register lock: a letter, not a chat reply
};
// Rule of thumb: stop at the marker. '{' beats '{"name":' unless you have a
// reason to dictate the first field too.
    
      
    4. 
      
  4. 
        
    4
    The mechanism — continuation is a function of the text so far
    
        
    This is the part the demo makes literal. The decoder never looks at "which run am I?"; it looks at the accumulated text and asks real questions of it — is a quote open, how deep is the brace nesting, which keys already appear. Those scans are why a prefill changes the output: it changes the answers.
    
        
    // STEP 4 — real state scans over the text written so far (the demo runs these).
function inOpenString(s){                       // odd number of unescaped quotes?
  let open = false;
  for (let i = 0; i < s.length; i++)
    if (s[i] === '"' && s[i-1] !== "\\") open = !open;
  return open;
}
function jsonKeys(s){                           // which "key": have been written?
  const re = /"([A-Za-z_][A-Za-z0-9_]*)"\s*:/g, out = [];
  let m; while ((m = re.exec(s))) out.push(m[1]);
  return out;
}
function braceDepth(s){ /* count { } outside strings */ }
function fenceOpen(s){ return (s.match(/```/g) || []).length % 2 === 1; }

// The decoder picks the next token from these answers — so seeding the text
// with a prefill genuinely puts it on a different path.
    
      
    5. 
      
  5. 
        
    5
    Validate the envelope, not just the content
    
        
    Score what actually breaks your pipeline. In the demo the baseline passes the content check on every task and fails every format check — which is exactly the failure prefill exists to fix, and exactly the failure a "did it get the answer right?" eval would miss.
    
        
    // STEP 5 — the real validators (5 + 3 + 3 + 3 = 14 checks).
const PREAMBLE = /^\s*(sure|certainly|of course|absolutely|here'?s|here is|great question|i'?d be happy|no problem|got it)/i;

json:    !PREAMBLE.test(raw)                       // no greeting
       && !raw.includes("```")                     // no markdown fence
       && parses(raw)                              // JSON.parse(raw) with no repair
       && raw.trim().endsWith("}")                 // no trailing chatter
       && valuesMatch(extractJson(raw))            // content correct (baseline passes)

label:   /^Label: (positive|negative|neutral)$/.test(raw.trim())
bullets: everyLineStartsWith("- ") && lines.length === 3
sql:     raw.trim().startsWith("SELECT") && raw.trim().endsWith(";") && !raw.includes("```")
    
      
    6. 
      
  6. 
        
    6
    Stop sequences, and re-attaching the prefill
    
        
    Prefill owns the start of the turn; a stop sequence owns the end. They are a pair. And because most APIs return only the tokens they generated, the prefill you sent is not in the response — concatenate it back before you parse, or your JSON.parse chokes on a fragment that starts at the second key.
    
        
    // STEP 6 — stop at the end of the line, then re-attach what you sent.
const PREFILL = "Label:";
const res = await callModel({ messages, prefill: PREFILL, stop: ["\n"] });

const full = PREFILL + res.text;    // "Label: negative"
//            ^^^^^^^ the API returned only " negative"

// The stop sequence itself is normally excluded from the returned text.
// Without stop:["\n"] this model keeps going: "\n\nWould you like me to
// explain the reasoning?" — and the exact-match check fails. Try it in LOOK.
    
      
    7. 
      
  7. 
        
    7
    Two rules that bite: the seam, and who owns the string
    
        
    Never end a prefill with whitespace — the join between your text and the generated text is a token boundary, and a dangling space makes the model complete a word that never started, or double the space. And never let an end user supply the prefill: it is the most direct steering lever in the whole API, and it is developer-owned text, like the system prompt.
    
        
    // STEP 7 — trim the seam; own the string.
const prefill = raw.replace(/\s+$/, "");   // "Label: " -> "Label:"
// "Label: " + " negative"  =  "Label:  negative"   <- double space, exact match fails

// NEVER:
//   prefill: req.body.userSuppliedPrefix        // user writes the model's mouth
// The prefill is trusted, developer-owned text. Treat it like the system prompt.
    
      
    8. 
      
  8. 
        
    8
    On current Claude models: use structured outputs instead
    
        
    A trailing assistant turn returns a 400 on Claude Opus 4.6 and later, Sonnet 4.6 and later, and Claude Fable 5 — prefill was removed as an affordance. Its jobs were split up: a JSON schema for shape, a tool with an enum for labels, and a plain system-prompt line for “no preamble”. Structured outputs are strictly stronger than prefill for JSON, because the schema is enforced rather than nudged.
    
        
    # STEP 8 — the replacement for a JSON-forcing prefill on current Claude models.
response = client.messages.create(
    model="claude-opus-5",
    max_tokens=1024,
    output_config={"format": {"type": "json_schema", "schema": {
        "type": "object",
        "properties": {
            "order_id": {"type": "string"},
            "customer": {"type": "string"},
            "total":    {"type": "number"},
            "status":   {"type": "string"},
        },
        "required": ["order_id", "customer", "total", "status"],
        "additionalProperties": False,
    }}},
    messages=[{"role": "user", "content": f"Extract the order fields.\n\n{doc}"}],
)
# No fence, no preamble, no repair step — the format is enforced, not requested.

# For a classification label: a tool with an enum, or the same json_schema with
#   {"label": {"type": "string", "enum": ["positive", "negative", "neutral"]}}
# For "no preamble" in prose: one system-prompt line does it.
    
      
    9. 
      
  9. 
        
    9
    Wire it up — one call site, two strategies
    
        
    If you ship across several models, put the choice behind one function: prefill where the runtime supports a trailing assistant turn, schema-constrained decoding where it doesn't, and the same parse + fallback on both paths. Keep the try/catch either way — neither approach makes a repair step pointless if a response is truncated.
    
        
    // STEP 9 — one shape, two strategies.
async function extract(doc, model){
  if (SUPPORTS_PREFILL[model]) {
    const prefill = '{\n  "order_id": "';
    const res = await call(model, {
      messages: [
        { role: "user",      content: `Extract the order fields.\n\n${doc}` },
        { role: "assistant", content: prefill },       // trailing turn = prefill
      ],
    });
    return safeParse(prefill + res.text);              // re-attach, then parse
  }
  const res = await call(model, {
    messages: [{ role: "user", content: `Extract the order fields.\n\n${doc}` }],
    output_config: { format: { type: "json_schema", schema: ORDER_SCHEMA } },
  });
  return safeParse(res.text);
}
function safeParse(s){ try { return JSON.parse(s); } catch { return repair(s); } }

    Copy-paste — the prefill request shape
    
        
    The whole technique on one screen: the transcript, the prefill as the trailing turn, the stop sequence, and the re-attach. Swap the prefill line per task from the table in step 3.
    
        
    {
  "messages": [
    { "role": "user",      "content": "{{task}}\n\n{{input}}" },
    { "role": "assistant", "content": "{{prefill}}" }
  ],
  "stop": ["{{stop}}"],
  "max_tokens": 512
}

# {{prefill}}  the SHORTEST prefix with only one plausible continuation.
#              No trailing whitespace. Developer-owned, never user-supplied.
# {{stop}}     where the turn should end ("\n" for a one-line label; omit for
#              a self-terminating format like JSON or a bulleted list).
# The response contains ONLY the generated text:
#     full = prefill + response.text     <- do this before parsing.

🎉 Day 59 of PromptFromZero done.
You learned assistant prefill, also called response priming: a chat request is a transcript with an empty assistant turn at the end, and you are allowed to write the first characters of that turn yourself. Because the model is autoregressive and cannot distinguish your tokens from its own, it continues rather than restarts — land it after { and the next token is a JSON key, land it mid-string and the next token is that string's contents. That converts the output format from something you request (and the sampler may ignore) into something that is already true of the transcript, which is why a one-character prefill routinely beats three paragraphs of formatting instructions: the whole argument is about the first token. You watched it run: a deterministic decoder whose every step is chosen by really scanning the accumulated text, scored by real validators — baseline 4/14, prefill 14/14, with the baseline passing every content check and failing every format check, because format was the entire failure. You also met the rules that travel with it — pair it with a stop sequence so the turn ends where you want, re-attach the prefill before parsing since APIs return only the generated text, never leave trailing whitespace at the seam, prefill the shape and never the values (a prefilled value gets confabulated rather than contradicted), and keep the string developer-owned, never user-supplied. And the honest state of play: current Claude models reject a trailing assistant turn with a 400 — its jobs moved to output_config.format for JSON, a tool enum for labels, and a system-prompt line for “no preamble” — while the mechanism stays native anywhere you control the raw prompt. Distinct from Day 16 (structured output — the schema side of the same problem) and Day 51 (system prompt — the turn before the conversation, not the one being written). 👉 Next up — LLM-as-judge: when the “right answer” is fuzzy (tone, helpfulness, faithfulness), grade outputs with a model against a rubric instead of an exact string.
