PromptFromZero · Day 61

🔣 Chain-of-Symbol prompting (CoS) — Hu et al., 2023. Chain-of-thought is words, and words are a terrible encoding of a spatial world: “the hall, which lies west of the pantry, has a door on its north side leading to the study” forces a reader to resolve which, resolve its, and hold a coordinate frame in working memory — and every one of those resolutions is a place to be wrong. CoS says: stop describing the world and serialize it. Define a tiny symbol table once, emit hall(1,0) study(1,1) and hall/study, and ask the model to reason in those same symbols. The prompt gets shorter, but the real win is that the state stops being ambiguous. Everything below is computed in your browser at run time: a random world generator, two serializers driven off the same state object, two real parsers, a BFS planner that gives provably-shortest ground truth, a hand-written tokenizer, and a live diff of parsed-vs-true. The solver half is an honest simulation with its assumptions printed on screen — the paper's real measured numbers are cited separately, and never mixed in.

The prose parser applies three documented shortcuts, the same ones a hurried reader takes: H1 resolve which/its to the nearest preceding room noun · H2 resolve it to the most recently mentioned room · H3 read your left allocentrically unless a facing was declared in the previous sentence. ⚠️ Be clear about which half of this page is which. The world generator, both serializers, both parsers, the BFS planner, the diff and the tokenizer are real code — the parse accuracy and the token counts above are measured, not stored. The solve rate is a simulation: there is no model on this page. Its assumptions, in full — A1 a fact must be recalled at the moment the plan step using it is emitted; A2 recall probability is floor + (1−floor)·e−d/L where d is the token distance from where the fact is stated to the end of the prompt, floor = 0.75, and L is the slider above; A3 a fact the parser misread is wrong no matter what; A4 a trial succeeds only if every fact on the shortest path survives A1–A3. Those constants are toy parameters, they are on screen, and you can move them. Nothing about the shape of that curve is evidence of anything — the evidence is below, and it is somebody else's.
📚 What the paper actually measured — cited, static, not computed here

Hu, Chen, Wu, Ru, Wan, Sun, Cheng, Wong — “Chain-of-Symbol Prompting Elicits Planning in Large Language Models” (2023). They build SPP, a spatial-planning benchmark of three simulated environments (Brick World, NLVR-based Manipulation, Natural Language Navigation), and compare chain-of-thought written in natural language against the same chains written in condensed symbols. On Brick World with ChatGPT they report accuracy rising from 31.8% to 92.6%, and prompt tokens falling by up to 65.8%. They also report that the gain is not uniform: it depends on the number of demonstrations and on the model, and CoS is a representation change, not a reasoning upgrade. Read the paper for the per-environment tables — do not quote my simulator.

🔑 The point is not brevity — it is that the symbolic form has exactly one reading. Slide verbosity to 0: the prose becomes a flat list of “The X is east of the Y.” sentences, and the prose parser scores 100% — because there is nothing left to resolve. Every point it loses above that comes from a genuine ambiguity that a human writer would produce naturally: a relative clause, an egocentric direction, a pronoun three sentences from its antecedent. The symbolic form never dips, at any verbosity, because there is no antecedent to find and no frame to carry. The token saving is real and it is nice; the disambiguation is the reason the technique works.

CoS = define a symbol table once, serialize the state into it, and make the model's intermediate steps symbolic too.

🔨 Build it yourself

    
Chain-of-Symbol is not a wording trick, and you cannot bolt it on at the end. It is a decision about what your prompt is made of: you stop generating prose about a state and start serializing the state itself. That means the work happens in your code, before the API call — a state object, a symbol table, a serializer, and a strict parser for the model's symbolic answer. Below is exactly what this page runs, in the order you would write it.

    
    

      
  1. 
        
    1
    Model the world as a state object first. The prompt is a view of it.
    
        
    The single most common mistake is writing the prompt by hand and letting the world exist only inside that string. Then you cannot check it, diff it, or re-serialize it. Build the state in code — rooms with coordinates, an edge list, object placements, a start — and treat both the prose version and the symbolic version as renderings of that one object. They can never drift, and you get a ground truth for free.
    
        
    // STEP 1 - the state. Everything else is a function of this.
const world = {
  rooms:   [ {id:0, name:"kitchen", x:0, y:0},
             {id:1, name:"hall",    x:1, y:0},
             {id:2, name:"pantry",  x:1, y:1} ],
  doors:   [ [0,1], [1,2] ],              // sorted, [min,max]
  objects: [ {name:"key", room:2} ],
  start:   0,
  goal:    "key"
};
// Canonical order everywhere (rooms by id, doors sorted, objects by name)
// so that serialize -> parse -> serialize is byte-identical.
    
      
    2. 

      
  2. 
        
    2
    Write the symbol table — once, at the top, and keep it tiny
    
        
    A symbol the model has to infer is worse than the word it replaced. Define every glyph in one short header line before any data, use the fewest distinct symbols that cover your relations, and never redefine one mid-prompt. Two or three lines of table buy you an entire prompt of unambiguous data — and the model can copy the table's own notation straight into its answer, which is what makes the answer parseable.
    
        
    # STEP 2 - the symbol table. This is the whole contract.
# a(x,y)=room at grid cell   a/b=door between a and b
# @a=you are here            a:o=object o is in room a
# *o=the object to find

# Rules for choosing symbols:
#   - one concept per symbol, no overloading
#   - ASCII you would find in code: ( ) , / : @ * - >
#   - avoid rare glyphs (see step 8) - they tokenize badly
#   - never use a symbol that also appears inside your data
    
      
    3. 

      
  3. 
        
    3
    The serializer: state → symbols, deterministic and sorted
    
        
    Sort everything. A serializer that emits doors in hash order gives you a different prompt for the same world on every run, which destroys prompt caching and makes your evals non-reproducible. Emit one line per kind of fact — cells, then edges, then state — so the model can find a fact by shape rather than by reading prose.
    
        
    // STEP 3 - serializeCoS. Same shape as the page's real one.
function serializeCoS(w, S){                 // S = the scheme (delimiters)
  const nm = r => S.pre + S.nameOf(r) + S.post;
  const cells = w.rooms.map(r => nm(r) + S.L + r.x + S.CS + r.y + S.R);
  const doors = w.doors.map(d =>
       nm(w.rooms[d[0]]) + S.DOOR + nm(w.rooms[d[1]]));
  const objs  = w.objects.map(o => nm(w.rooms[o.room]) + S.OS + o.name);
  return [ symbolTable(S),
           cells.join(" "),
           doors.join(" "),
           S.HERE + nm(w.rooms[w.start]) + " " + objs.join(" ")
             + " " + S.GOAL + w.goal ].join("\n");
}
// Two rooms, one line each, no adjectives, no clauses, no pronouns.
    
      
    4. 

      
  4. 
        
    4
    Make the model's intermediate steps symbolic too — that is the “chain”
    
        
    Halfway CoS is the most common way to get none of the benefit: people symbolize the input and then let the model narrate its reasoning in English. The chain is where the state is being updated step by step, so the chain is exactly where ambiguity does the damage. Show one worked example in the symbol language and the model will copy the format — that is all the demonstration has to do.
    
        
    // STEP 4 - one demonstration, in the answer language you want back.
const DEMO =
`Example:
@kitchen -> kitchen/hall -> @hall -> hall/pantry -> @pantry  DONE`;

// Each arrow is a state transition; each door symbol is the edge used.
// The model is now doing symbol rewriting, not prose composition -
// and every intermediate state is a token you can check against
// the world you serialized.
    
      
    5. 

      
  5. 
        
    5
    Parse the answer strictly, and fail loudly
    
        
    A symbolic answer is worth having because it is machine-checkable. Do not regex out the room names and shrug at the rest — validate every transition against the world you serialized, so a hallucinated door is caught in your code and never reaches a user. If parsing fails, that is a signal worth logging: it usually means your symbol table was ambiguous, not that the model is bad.
    
        
    // STEP 5 - parse + VALIDATE. The validation is the point.
function parsePlan(txt, w){
  const path = [], seen = txt.match(/@([a-z]+)/g) || [];
  for (const t of seen) path.push(t.slice(1));
  if (!path.length) throw new Error("no @room tokens in answer");
  if (path[0] !== w.rooms[w.start].name) throw new Error("wrong start");
  for (let i = 0; i + 1 < path.length; i++){
    if (!hasDoor(w, path[i], path[i+1]))
      throw new Error("hallucinated door " + path[i] + "/" + path[i+1]);
  }
  return path;                       // now provably walkable in the real world
}
    
      
    6. 

      
  6. 
        
    6
    Keep a ground-truth planner in code — and notice what it tells you
    
        
    Once the world is a real graph, BFS gives you the provably shortest plan in ten lines. That is your grader. It is also an uncomfortable question: if you can compute the answer exactly, why are you asking a model at all? The honest answer is that CoS is for the cases where the state extraction is the hard part and the search is easy — you use the model to read a messy human description into symbols, and then you plan in code.
    
        
    // STEP 6 - BFS. Deterministic neighbour order = reproducible plans.
function planBFS(w){
  const adj = adjacency(w), prev = w.rooms.map(() => -1);
  const seen = w.rooms.map(() => false), q = [w.start];
  seen[w.start] = true;
  for (let h = 0; h < q.length; h++)
    for (const v of adj[q[h]])
      if (!seen[v]){ seen[v] = true; prev[v] = q[h]; q.push(v); }
  // walk prev[] back from the goal room -> shortest path, always
}
// Grade three ways: OPTIMAL (== BFS length),
// VALID-BUT-LONGER (walkable, not shortest), INVALID (uses a fake door).
    
      
    7. 

      
  7. 
        
    7
    Measure three things, not one
    
        
    Token count is the number everyone reports and the least interesting of the three. Measure round-trip fidelity (serialize → parse → deep-equal the original state), answer parse rate (what fraction of responses your strict parser accepts), and only then task accuracy. A CoS rollout that saves 60% of tokens and drops your parse rate to 80% is a regression wearing a nice hat.
    
        
    # STEP 7 - the three numbers, in priority order.

# 1. ROUND-TRIP FIDELITY  (must be 100%, it is your own code)
assert canon(parseCoS(serializeCoS(w))) == canon(w)

# 2. ANSWER PARSE RATE    (strict parser accepts the model's reply)
parse_rate = accepted / total          # target: > 0.98

# 3. TASK ACCURACY        (optimal / valid / invalid, vs BFS)
optimal_rate, valid_rate, invalid_rate

# and only then:
# 4. tokens_cos / tokens_nl - the headline that sells it internally

  8. 
        
    8
    The tokenizer trap — count, do not assume
    
        
    “Symbolic” feels like it must be shorter, so people reach for beautiful rare glyphs and quietly make the prompt more expensive. Tokenizers are trained on text; common ASCII punctuation is cheap, and a rare Unicode glyph frequently falls back to several byte-level pieces. Flip the scheme selector in LOOK to exotic glyphs and watch the token count go the wrong way — that is the whole lesson, live.
    
        
    # STEP 8 - always measure the scheme, never guess it.

kitchen(0,0)      # names + coords   - readable, no legend
K(0,0)            # letters + legend - usually the cheapest
⟨K⟩⟦0,0⟧         # exotic glyphs    - looks symbolic, costs MORE

# The test that settles it, before you ship the scheme:
for scheme in SCHEMES:
    n = count_tokens(serialize(world, scheme))
    print(scheme.id, n)      # use the real tokenizer for YOUR model
# tiktoken / the provider's count-tokens endpoint. Not your intuition.
    
      
    9. 

      
  9. 
        
    9
    Know when to fall back to words
    
        
    CoS strips out exactly the thing that makes an LLM useful on some tasks: the meaning carried by the words. If the task needs world knowledge — that a kitchen has a fridge, that a “cellar” is probably below ground, that “fragile” changes how you handle a box — symbolizing it deletes the prior you were relying on. Symbolize the structure, keep the words that carry semantics. A hybrid prompt is usually the right answer.
    
        
    # STEP 9 - the decision, honestly.

USE CoS when:
  - the state is combinatorial and gets restated every turn
  - relations are the payload (adjacency, order, containment, coords)
  - you can check the answer in code afterwards
  - prompts are long enough that attention distance is real

DO NOT use CoS when:
  - the answer depends on what the words MEAN, not how they relate
  - the state is small enough to state plainly in three sentences
  - your users read the prompt (symbols are hostile to humans)

# HYBRID is usually correct:
#   symbols for the graph, plain words for the properties.
#   pantry(1,1) pantry:fragile-crate  <- keep "fragile", it is the prior.

🎉 Day 61 of PromptFromZero done.
You learned Chain-of-Symbol prompting — Hu et al., 2023 — which starts from a specific failure: chain-of-thought on spatial and planning tasks writes the world state out in natural language, and natural language is a bad encoding of a world. Prose forces the reader to resolve pronouns, chase relative clauses, and carry a coordinate frame across sentences, and each of those is a place to be wrong. CoS replaces the wordy description with a compact symbolic serialization — a symbol table defined once, then coordinates, edges and markers — and, crucially, asks the model to write its intermediate steps in those same symbols, so the chain itself becomes symbol rewriting rather than prose composition. On this page you watched a real world get serialized two ways from one state object, parsed back by two real parsers, and diffed against ground truth: the symbolic round-trip is lossless at every setting, while the prose parser loses points to genuine ambiguities that any human writer would produce — and recovers to 100% at verbosity 0, which is the proof that the failures are ambiguity, not a broken parser. The token saving is real, but it is the second benefit; the first is that a symbolic state has exactly one reading. You also saw the two traps: the tokenizer trap, where pretty rare glyphs cost more tokens than the words they replaced (flip to the glyph scheme and watch the count rise), and the semantics trap, where symbolizing a task that needed world knowledge in the words deletes the prior you were relying on. Symbolize the structure; keep the words that mean something. 👉 Next up — LLM-as-judge: when the “right answer” is fuzzy (tone, helpfulness, faithfulness), grade outputs with a model against a rubric instead of an exact string.
