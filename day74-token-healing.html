Two numbers on this page are declared and everything else is a count. WHAT IT COSTS

Healing is a prompt-side edit, so its bill is the prompt's token count. Every rule here removes tokens rather than adding them, which has a second consequence worth more than the saving: a shorter prompt is still a prefix of the longer one, so none of these rules can invalidate a prefix cache.

The last thing you type is not the last thing the model reads

A prompt is a string to you and a list of integers to the model. Between the two sits a tokenizer, and a tokenizer is not a formatter — it is a segmenter with opinions. Given the text https://example.com it will produce a handful of tokens, one of which is very likely the whole of https, because that string occurs often enough in the training corpus to have earned an entry. Now end your prompt one character earlier. The tokenizer cannot produce https, because the fifth character is not there, so it produces http instead. Your prompt's token list is now a list that never appears in front of the text you were asking for, because in that text those four characters are always the first four fifths of a single token.

That is the entire subject of this page. It has a name — token healing — and a standard fix: rewind the last token, and constrain the first generated token to begin with the text you removed. Everything else here is measurement of that fix, of the cheaper thing you could do instead, and of the two places where the fix does damage that no test would catch, because a prompt that ends mid-token returns HTTP 200 and a completion that looks like a completion.

The lemma the page rests on

There is one clean fact underneath all of it. Let T be the text the model is going to write and P a prefix of it — your prompt. Then the tokenization of P is a prefix of the tokenization of T exactly when the length of P is a token boundary of T. One direction is arithmetic: if the tokens agree, the lengths sum to a boundary. The other is the interesting one, and it holds for both segmenter families here for the same reason — no token of T crosses a boundary of T, so the region in front of that boundary is segmented without ever consulting a character behind it. The page does not take this on trust: it checks it cut by cut, on 1,029 cuts under each of four tokenizers, and reports the violation count.

What the lemma buys is that "off-distribution" stops being a vibe and becomes a decidable test. The prompt is fine if its length is a boundary of the intended text and broken if it is not, and both are computable from the two strings. That is why this page can prove things about a phenomenon that is usually discussed in anecdotes.

The parameter-free part: one token, five cuts

Take const url = "https and remove characters from the end. Five of the resulting prompts stop somewhere inside https. Only the last of them is a boundary. The other four hand the model a token list it has never seen in that position, and they do not all cost the same: cut after http and the reader has one off-boundary step to survive, cut after h and it has four, because the truncated prompt shattered into single characters and the model has to re-spell its way back to the boundary.

Now apply the shipped rule to each. After http it is perfect: rewind that one token, demand a token beginning http, and the tokenizer's own choice — https — satisfies the constraint, so the seam is gone. After h it is also perfect, for the same reason. In between, after ht and htt, it is worse than doing nothing, because rewinding one token there rewinds one character, which does not reach the boundary at all — it just gives the reader one more off-boundary step to get through. Two fixed, two damaged, one that needed nothing, and no parameter anywhere in the panel.

The advice that is really about a vocabulary

"Do not leave a trailing space at the end of your prompt" is the single most repeated piece of tokenizer folklore, and it is correct — for the tokenizers it was written about. In a GPT-style vocabulary a word carries its leading space:  the is one token and the is another. A prompt ending in a space therefore lands in the middle of the next word's token before that word has been written, and the model must produce a token beginning with a letter where the text has one beginning with a space. In a WordPiece-style vocabulary the space is its own token, and the same cut is a clean boundary.

Measured over the same corpus with the same segmenter, cuts after a space are off-boundary 69.40% of the time under the space-attached vocabulary and 8.96% under the space-separated one. That is a fact about the vocabulary and not about prompting, and it has a consequence the advice does not carry: stripping trailing whitespace is worth +16.13 points on prose, −1.10 on JSON and −4.24 on a field list, because in JSON the space after a colon is part of ": " and removing it moves the cut from one non-boundary to a different, deeper one. The rule that is nearly free is also the rule that can be negative, and the sign depends on what you asked for.

Depth, and why one token is the wrong number

Every implementation of token healing removes exactly one token. The rewind the intended text actually requires is exactly one token on 36.82% of off-boundary cuts and reaches seven. The reason is not exotic: a truncated long token shatters. Cut ```json after ```js and the prompt is not one broken token but two — ``` and js — so rewinding one of them leaves you inside the other. The fix that follows from the mechanism is to keep rewinding while the accumulated text is still a proper prefix of some vocabulary entry, and it lifts the clean-cut share from 36.82% to 65.08%.

But only with the right constraint. Rewind two tokens and keep demanding that the next single token begin with everything you removed, and you have asked for a vocabulary entry starting with a two-token string. On this corpus that entry does not exist on 589 of 736 off-boundary cuts — the constraint set is empty — and the intended text becomes unreachable rather than unlikely. That row is the only one on the page that is still below 100% when the seam has been declared costless, because unreachability is not a probability. The trie walk, which permits a token that is a prefix of what you removed and keeps owing the rest, has no such failure and costs one extra branch in the decoder.

What actually wins

Not the feature. Rewinding to the start of the current word — keep removing tokens until you remove one that begins with a space or a newline — delivers 90.37% against the shipped rule's 60.35% and the control's 40.42%. It hurts 1.22% of off-boundary cuts instead of 39.67%. It sends fewer prompt tokens than the oracle does. And it needs the vocabulary only for the trie constraint, not for the decision of where to stop, because "the last space" is a property of your string.

The reason it wins is the same reason depth-1 loses: a boundary is much more likely to sit at the start of a word than one token back from an arbitrary character. That is a statement about vocabularies, not about models, and it is why the rule survives the tokenizer control — 83.56%, 81.78%, 83.46% and 82.57% clean across the four.

Where the page states its assumptions

Two numbers are declared. Set horizon to 0 — assume the damage does not reach past the first step — and eight of the nine policies come back bit-identical at 100.00%, which is the honest null: if a seam costs nothing, healing is worth nothing. The ninth is the unreachable row, and it is where an assertion of mine failed: the panel was built claiming all nine, and unreachability is not a probability, so declaring the seam free does not make a text spellable that no permitted token can spell. Setting recover to 1 has the same shape and the same single exception. In between, the ordering of the policies does not change at any setting of either dial, and the one finding that is horizon-dependent — that the shipped rule hurts as well as helps — is reported with its horizon beside it: 0.00% of cuts at horizon 1, 14.67% at 2, 31.93% at 4. The net gain is positive at every setting.

What this is not

It is not a claim about a specific tokenizer. The vocabulary is hand-written and its properties are declared; change which entries are proper prefixes of which and which cuts misalign changes, while the existence of the seam does not. It is not a claim about a specific model either: nothing here models language, and the reader always intends to write the target text. What is measured is how many steps the harness makes it spend in a token sequence that cannot occur, and what each repair does to that number.

It is also not Day 59 and not Day 73. Day 59 seeded a trailing assistant turn to lock the reply's format, and treated the prefill as a string. Day 73 was the other end — where the reply gets cut and what the harness hands back. This page is the seam between them: the last token of what you send, which is the one place a prompt can be wrong without a single character of it being wrong.

🔨 How it is built

Every number on the MEASURE tab comes from the block between ENGINE:BEGIN and ENGINE:END in this file's source. It touches no DOM, reads no clock and calls no random number generator. An independent Node verifier rebuilds each load-bearing structure a second way — a charCode trie instead of a first-character index, a full enumeration of every segmentation instead of a dynamic program, trie descent instead of a filter over the vocabulary list — and compares them item for item.

1. The corpus is data and the cuts are enumerated

Twenty target texts across seven families — JSON, code, URLs, prose, markdown, a field list, tags — and every interior character position of each one is a cut. That is 1,029 cuts, and every rate on the page is a count over them or over a named subset, so there is nothing to resample and no confidence interval to quote.

2. Two vocabularies, one of them derived

The space-attached vocabulary is hand-written; the space-separated one is derived from it by removing the leading space from every entry that has one, so the two differ in exactly the property under test and in nothing else. Every character in the corpus is a token, which makes both vocabularies total — there is no unknown-token path and no string that cannot be produced. Three entries are deliberately awkward so that longest-match is not always the fewest-token segmentation; without them the two segmenters would agree everywhere and the control would say nothing.

3. Two segmenters from two real families

Longest match, left to right, which is the WordPiece shape; and fewest tokens with ties broken toward the longer first token, which is the Unigram shape at equal unit costs. The second is a dynamic program over suffix costs in the page; the verifier re-derives it by enumerating every segmentation of every string and taking the minimum, which is a different algorithm and a different tie-break implementation reaching the same answer.

4. The reader is declared in five clauses, and they are in the source

It always intends to write the remaining target text; its next token is the first token of the tokenizer's own segmentation of that text; a step is on-seam when the decoded length is not a boundary of the intended text's tokenization; the harness may constrain the first emitted token, substituting the longest permitted entry that still matches when the intended one is refused; and if no permitted entry matches, the text is unreachable. Delivery is recover raised to the number of on-seam steps, capped by horizon. There is no language model in it, which is the point: the quantity being measured is the harness's contribution alone.

5. Nine policies, each written from its English description

Do nothing. Rewind one token and force the same token back — which is bit-identical to doing nothing, and is asserted to be. Strip trailing whitespace. Rewind one token if some longer entry extends it, with the must-extend constraint, and again with the trie constraint. Rewind while extendable, with each constraint. Rewind to the last space-initial token. And an oracle that rewinds to the intended text's own boundary, which is not implementable and is labelled as the upper bound it is. Each policy also reports whether it acted, because a rule that declines returns the control exactly and one class of cut makes every rule decline.

6. The walk stops early, and that is a lemma too

Once the reader is on a boundary with nothing owed, every remaining step is on-boundary and contributes nothing, so the walk stops there instead of running to the end of the text. The verifier does not: it walks every step to the end of every string and compares the counts, which is how the early stop is checked rather than assumed.

7. The extension set is the whole of what a harness can know

At heal time the only fact available is which vocabulary entries begin with the removed text. The set always contains that text — it is a token — so healing is always feasible at depth one; and when the set contains nothing else, the constraint permits exactly the token that was already there, so the rule declines. The page counts that class rather than smoothing it away, and the verifier rebuilds the same sets by descending a trie.

8. The claims are attacked, not restated

The in-page assertions check the lemma on every cut under every tokenizer; that the oracle leaves no seam anywhere; that forcing the token back is bit-identical to the control on every cut; that healing a cut which was already a boundary changes nothing; that the extension set always contains the removed text; that delivery is monotone in both declared numbers; and that every policy's aggregate equals the mean of its per-cut values. The verifier re-derives all of it from its own oracle stack and re-checks every number quoted in the headline against the engine.
