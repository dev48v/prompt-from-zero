✂️ Edit formats — when you ask a model to change a document rather than write one, the prompt names a shape for the answer: the whole file back, a search block and its replacement, a unified diff, a line range, an anchor line. That choice is usually argued about as a token bill. It is not. It decides which of your failures you are told about. Nothing here simulates language ability — nine documents are DATA, all 507 edit sites are enumerated, and every reply is serialized by a real emitter, put through a real string transformation and applied by a real applier, so an outcome is decided by running the code and never by a formula. Exactly three numbers are declared, all three on sliders and all three labelled where they are used. The parameter-free centrepiece needs no dial at all: put three hunks in one call, enumerate every one of the 11,883 disjoint triples in the corpus, and line ranges applied top-down are wrong on 93.14% of them and refuse 0.00% — while the same three edits as a unified diff are wrong on 0.00% and refuse 95.16%. Same model, same call, same information. The format did not change how often it went wrong; it changed whether anything said so. 🔴 And the repair is free: sort the hunks by line number descending and line ranges come back at exactly 100.00%, which is an identity and not a measurement. 🔴 The defect is invisible to the test everyone writes: on all 507 single-hunk edits with nothing else going wrong, line ranges score 100.00% delivered and 0.00% silent. One hunk cannot express the bug. 🔴 Two recommendations of mine died under measurement. The obvious cure for whitespace drift — match the search block whitespace-insensitively — drops delivery from 97.11% to 84.53%, because what it makes applicable is the model's re-indented copy: in a search/replace block the surrounding lines are part of the replacement, and in a diff they are only part of the locator, so a drifted context line can land in your file in one format and can only fail to match in the other. And "add context lines to be safe" has a ceiling that nobody quotes: search/replace peaks at k = 3 — which happens to be the width every tool ships — and loses 2.56 points by k = 6 while its bill rises by half; a unified diff peaks at k = 0, at 99.83% for 57.4 output tokens, so the best cell on the page is also the cheapest one — a line number already locates the hunk and the removed lines already verify it, which makes every context line one more line that can come back wrong and buys nothing. 🔴 The whole-file rewrite, the format people fall back on when a patch misapplies, is the worst row here at 51.34% delivered — and it is the only row with 0.00% loud failures, which is the same fact twice: there is nothing to check it against, so every defect it has is silent. Its damage is split on the page rather than lumped: 31.96% cosmetic against 16.70% substantive. 🔴 Two null results, located rather than claimed: fencing the reply is worth exactly 0.00 on all ten harnesses, and patch fuzz is worth exactly 0.00 on all 507 single-hunk edits at all six context widths — then worth +69.38 points on the triples, the same feature, unchanged. And the control: confining a style change to one line instead of the whole re-typed block moves every one of the ten rows by 0.00 and reorders nothing. Free beats paid three times over: refusing a search block that matches twice costs 0 output tokens and takes silent corruption to 0.00%; a size guard on a whole-file answer costs 0 output tokens and takes substantive corruption from 16.70% to 6.77% with 0.00% false refusals; and the unified diff beats search/replace on both axes at once — 97.56% against 97.11% for 0.683× the bill. 223,377 in-page assertions plus 1,167,169 in an independent Node verifier that rebuilds the matcher as a rolling-hash index, the diff applier as a state machine over a token stream, the uniqueness ladder by suffix-array sorting and the triple enumeration as an independent reference splicer. Pure vanilla JavaScript, one file, no build step.

Three numbers on this page are declared and everything else is a count. drift is the probability that a single line the model had to RE-TYPE comes back changed in a way that changes no meaning — and it is per line, which is the whole point: a format that asks for forty lines back is forty times as exposed as one that asks for four, so the probability an emission is clean is (1 − drift) raised to the number of lines it re-typed. chatter is the probability the reply arrives wrapped in a sentence, half of those inside a fence and half not. elide applies only to a whole-document answer: the probability it replaces its longest untouched run with a placeholder line. Set all three to zero and the page tells you what is structural rather than accidental. Everything else — every match, every parse, every splice, every token count, every one of the 507 sites and 11,883 triples — is real string code over a finite enumerated set, so a 0.00% here is a zero and not "none seen".

The format decides which failures you hear about

Ask a model to change a document and you have to tell it what the answer should look like. There are five shapes in common use. Send the whole file back. Send a block to find and a block to put in its place. Send a unified diff. Send a line range and its replacement. Name an anchor line and say what goes after it. Every discussion of this choice I have read is about the token bill, and the token bill is the least interesting thing about it.

Here is what the page found instead. The five formats fail at broadly similar rates. What differs, enormously, is what happens when they fail. A search block that matches nothing is a refusal you can retry. A line range applied to a file that has already shifted is a splice into the wrong place, and it returns success. The first is a bad afternoon. The second is a corrupted file with a green tick next to it.

The instruction is written against a file that no longer exists

Put three changes in one reply, which is the ordinary case. The model saw one document and numbered its hunks against that document. Your harness applies them one at a time. After the first hunk, if it added or removed a line, every number below it is off by that much — and the model was never wrong, it never saw the intermediate file, it could not have numbered against it.

Apply them from the bottom up and the problem disappears completely, because an edit low in the file cannot move anything above it. That is an identity, not a tuning: every one of the 11,883 triples the page enumerates comes back exactly right. Apply them top-down and 93.14% of them come back wrong, and because a line range carries nothing to verify against, all 93.14% come back wrong silently.

Give the same three edits to a unified diff applier and the wrongness rate is 0.00%. Not because a diff is cleverer about ordering — it is applied in exactly the same broken order — but because a diff carries the lines it expects to find and the applier compares them before it writes. When the file has shifted, the comparison fails and the applier stops. 95.16% refused, 0.00% wrong. The information content of the two replies is identical. One of them is checkable and the other is not.

A search block is a query, and a query can have more than one answer

Search/replace avoids line numbers entirely by naming the text instead. That works until the text occurs twice, which in real documents it does constantly: two identical stanzas in a config, two identical catch blocks, a repeated key in an env file. On this corpus 30.57% of sites have a one-line search block that occurs more than once, and in 55.48% of those the intended one is not the first hit.

The standard answer is context: include the surrounding lines until the block is unique. The page enumerates the smallest context that works for each site, and it is small — 69.43% of sites need none at all, 98.42% are covered by three lines each side, and the worst site in the corpus needs five. So context does solve ambiguity, and it solves it quickly.

It is what context costs that nobody prices. Every context line is a line the model has to re-type, and a re-typed line is a line that can come back with different indentation. Past the point where uniqueness is already won, more context is pure exposure. Search/replace peaks at three context lines — which is, by luck rather than by argument, the width the tools ship — and falls away above it; a unified diff peaks at zero, because a diff already carries a line number to locate the hunk and the removed lines to verify it, and the context lines are doing no work at all that the removed lines were not already doing.

Where the surrounding lines end up

This is the mechanical difference between the two patch formats and it is worth stating on its own. In a unified diff the context lines are input to the applier: it reads them, checks them and throws them away. In a search/replace block the surrounding lines appear twice — once in the search half and once again in the replacement half — and the replacement half is what gets written to disk. So the same defect has two different consequences. A context line that came back re-indented makes a diff fail to apply. It makes a search/replace block succeed and write the re-indented line into your file.

That is why the obvious fix backfires. Matching whitespace-insensitively removes every drift-induced refusal — it is guaranteed to, by construction, because the normaliser collapses exactly the differences that drift creates. And it converts them into applications of the drifted text. Delivery goes from 97.11% to 84.53%. The 15.20% it gains in "applied" is 15.20% of files that now differ from what you asked for. It is nearly all cosmetic, and the page counts it as cosmetic rather than lumping it in, because a whitespace diff nobody asked for is a real cost and not the same cost as a deleted line.

Why the safe fallback is the worst row

When a patch format misapplies, the reflex is to ask for the whole file back. It cannot misapply: there is nothing to locate and nothing to match. That is exactly the problem. Every other format on this page has some check between the reply and the disk, and a check that fails is a refusal. A whole-file answer has no check, so its failure rate and its silent failure rate are the same number: 48.66% at the default dials, against 0.00% for either patch format.

And it is the most exposed format there is, because it re-types the entire document: 21.71 lines against a diff's 7.33. Exposure is not a metaphor here, it is the exponent. Then there is the failure only this format has — the answer that says // ... rest of file unchanged ... in the middle. A three-line size guard catches most of those, costs nothing, and refuses none of the legitimate edits. It is the single best-value line of code on the page and it still leaves the format last.

What this is not about

Day 70 measured how an output format survives a preamble, and this page inherits the answer rather than re-deriving it: the formats with a closing marker survive prose around the answer untouched, and the ones with only an opening marker take the following sentence into the document. Day 73 was about where a reply gets cut, and Day 74 about where a prompt does. This page is about none of those. It is about the reply being an instruction rather than a document, and about the fact that an instruction can be checked before it is carried out.

If there is one sentence to keep: ask for the format that lets your harness refuse. Then let it refuse.

🔨 How it is built

Every number on the MEASURE tab comes from the block between ENGINE:BEGIN and ENGINE:END in this file's source. It touches no DOM, reads no clock and calls no random number generator. An independent Node verifier rebuilds each load-bearing structure a second way — a rolling hash instead of a line-by-line scan, a state machine instead of a line-prefix switch, a sorted suffix table instead of a repeated search, an independent reference splicer instead of the appliers — and compares them item for item.

1. The corpus is data and the edits are enumerated

Nine documents across seven families — config, YAML, code, SQL, markdown, JSON and a flat env list — written out line by line in the source. Three of them carry byte-identical regions on purpose, because that is the hazard under test, and one is a single block written out twice so that the minimum-context ladder has a top end that is not an accident. An edit site is a start line and a span of one, two or three lines: 507 of them, every one enumerated, so every rate on the page is a count over a finite set.

2. The replacement is derived by one content-driven rule

Bump the first numeral in the span if there is one; otherwise append a comment line at the same indentation. That rule is not decoration. It is what makes 97.93% of the enumerated triples contain at least one edit that changes the document's line count, which is the only reason a stale line number can be caught at all — and the exact 6.86% of triples that top-down application survives is the set where no length change happens above a later hunk.

3. Five emitters that write what a model would have to write

A whole document, a search/replace block with its three markers, a unified diff with an @@ header and prefixed lines, a line-range instruction, and an anchor instruction. Each returns the literal reply string and, separately, the number of existing document lines it required the model to copy. That second number is the page's exposure measure and it is what the drift dial is raised to the power of.

4. Four parsers written the way real ones are written

Each one scans for its marker rather than assuming the reply starts with it, which is what makes a preamble harmless. What separates them is the other end: search/replace has a closing marker, a diff has a self-terminating line grammar, and a line-range or anchor instruction has nothing at all — so everything after the header is the payload, including the sentence the model added afterwards. That is a structural property of the format, not a bug in the parser, and the parameter-free chatter panel is where it shows up as 100.00% against 0.00%.

5. Six appliers, and an oracle that is not one of them

Exact line matching, whitespace-insensitive matching, first-match and refuse-unless-unique, diff context verification with and without fuzz, a line splice with no verification at all, an anchor lookup, and a whole-file replace with a size guard. The result of each is compared line for line against the document the edit was supposed to produce, which is built independently of every applier. Three outcomes: correct, refused, or applied-and-wrong — and the last is split into cosmetic and substantive, because a file that differs only in whitespace and a file with a line missing are not the same event.

6. Emission states are enumerated and then weighted

Four drift kinds, three chatter kinds and two elision states, and the applier is run for every combination that a format can reach. Only then are the declared numbers used, as weights, so nothing on the page is sampled: a rate is a weighted sum over outcomes that were each computed by running real code. The probability that an emission is clean is (1 − drift) raised to the number of re-typed lines, which is how a per-line dial becomes a per-format exposure. One retry after a refusal is allowed, drawn independently, and that independence is an assumption rather than a measurement — so it is stated here and the un-retried columns are on the table too.

7. The drift model has its own control

A style change could reasonably be systematic or a single slip. The page assumes systematic and then recomputes the entire scoreboard the other way, confining the change to one line. The control panel prints the gap for every row and how many places the ranking moved. Both are zero, which is what a control is for: it says the formats are doing the work rather than the assumption.

8. The claims are attacked rather than restated

The in-page assertions check that the two search/replace harnesses emit bit-identical replies and differ only in the check; that the two whole-file harnesses do too; that the guard refuses no legitimate edit; that fuzz changes nothing on a single hunk; that a fenced reply is indistinguishable from a bare payload after extraction; that the hand-written token scanner agrees with the regular expression it replaced on every payload; that every weight set sums to one; that delivery is monotone in each declared number; that a cosmetic difference really is whitespace-only; and that the minimum-context ladder agrees with the ambiguity census at every width. The verifier re-derives all of it from its own independent stack and then re-checks every number quoted in the headline against the engine.
