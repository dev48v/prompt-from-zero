PromptFromZero · Day 57

🧪 Prompt Evals — the practice of treating a prompt like code you can test instead of a thing you eyeball. The moment a prompt matters, tweaking it and skimming one or two outputs to decide it “feels better” stops working: you can't see the case it quietly broke, and the next tweak silently un-fixes the last one. Eval-driven prompt development replaces the vibe check with a measurement. You pin down a small test set — inputs paired with an expected answer or an assertion — write two or three candidate prompt variants, run every variant against every test, and let deterministic graders (exact-match, contains, regex, JSON-valid, or a simple rubric score) turn each (variant × test) into a pass/fail and a number. The payoff is a results matrix: variants across the columns, tests down the rows, a per-variant pass-rate and average score, a highlighted winner — and, crucially, a regression view. Because a prompt change can lift the overall pass-rate while quietly breaking a case that used to pass, you diff the candidate against a baseline and catch the test it dropped before shipping. This is “promptfoo-style” eval, and this page is genuinely interactive with no API and no network: a self-contained JS harness with 3 variants, 5 tests, deterministic canned model outputs and real graders — toggle a grader type or edit an assertion and watch the matrix, the pass-rates, the winner and the regression diff recompute live. Distinct from Day 56 (Cognitive Verifier — a reasoning pattern); this is the discipline that stops any prompt change from silently dropping quality.

Stop eyeballing prompt changes — measure them. Run 3 prompt variants against a test set, grade every cell, and read the winner — then catch the regression a higher pass-rate is hiding.

🔑 A prompt eval turns “this feels better” into a number you can defend — and defend against. The matrix does two jobs at once. First it ranks: run every variant against the same fixed test set, grade each cell deterministically, and the winner is simply the column with the highest pass-rate (tie-break on average score) — no vibes, no cherry-picked example. Second, and more important, it guards: a change almost never strictly dominates. V3 adds few-shot examples that finally catch the urgent cases V2 missed (pass-rate 60% → 80%) — but the same examples make it over-trigger urgent on a friendly thank-you, so it regressed a test V2 passed. A single headline number would have hidden that. The regression diff makes it impossible to miss: improved cells in green, the dropped cell in red. That's the whole discipline — measure every candidate on the same set, pick the winner by pass-rate, and diff against the baseline so a net-positive change can't silently ship a net-negative surprise.

Prompt evals = a fixed test set + candidate variants + deterministic graders → a results matrix, a pass-rate winner, and a regression diff. Measure prompts; don't eyeball them.

🔨 Build it yourself

    
A prompt eval is just a small harness: a test set, a list of candidate prompts, a set of graders, and a loop that fills a matrix. Below is the exact harness the demo runs — plain, dependency-free functions you can lift into any project — followed by the equivalent promptfoo YAML config so you can run the same thing from the CLI and gate it in CI. Same idea both ways: measure every candidate on the same set, pick the winner by pass-rate, and fail the build on a regression.

    
    
      
  1. 
        
    1
    The idea in one line — stop eyeballing, start measuring
    
        
    Eyeballing a prompt change tests one input you happened to look at, and forgets it the moment you move on. An eval pins a fixed test set so every change is scored on the same cases — the winner is defensible and a regression is visible.
    
        
    // Eyeballing  →  test one case, forget it, hope:
//   tweak prompt → glance at ONE output → "yeah better" → ship
//   (the case you broke is invisible)
//
// Eval-driven  →  measure every candidate on a fixed set:
//   test set × variants → graders → matrix
//   → pass-rate winner + regression diff  (defensible + safe)

  2. 
        
    2
    Define the test set — inputs + an expected answer / assertion
    
        
    Each test is an input plus how to judge the output. Keep a fixed, versioned set (and a separate holdout you don't tune against, so you don't overfit the prompt to the tests). Cover the easy cases and the edge cases that bite.
    
        
    // STEP 2 — the test set: input + grader + assertion.
const tests = [
  { input: "I was charged twice this month.",
    grader: "json_valid" },                       // must return JSON
  { input: "How do I reset my password?",
    grader: "contains", assertion: "account" },
  { input: "The whole site is down, nobody can log in!",
    grader: "regex", assertion: '"urgent"\\s*:\\s*true' },
  { input: "Just wanted to say thanks!",
    grader: "exact_match",
    assertion: '{"category":"feedback","urgent":false}' },
  { input: "Payment failed and I can't access my account.",
    grader: "rubric", assertion: 'billing, "urgent":true, access' },
];
    
      
    3. 
      
  3. 
        
    3
    Define the candidate variants — the prompts you're comparing
    
        
    A variant is one prompt strategy for the task. Change one thing at a time (add a schema, add few-shot examples) so the matrix tells you which change moved the number. In the demo these three are V1 naive, V2 + JSON schema, V3 + few-shot.
    
        
    // STEP 3 — the candidate prompts (one variable per step).
const variants = [
  { id: "v1", system: "Classify this support email." },
  { id: "v2", system: "Classify the email. Return ONLY JSON " +
                       '{"category": string, "urgent": boolean}.' },
  { id: "v3", system: "Classify. Return ONLY JSON {category,urgent}. " +
                       "Examples:\n" +
                       '"site is down" → {"category":"technical","urgent":true}\n' +
                       '"payment failed, locked out" → {"category":"billing","urgent":true}' },
];
    
      
    4. 
      
  4. 
        
    4
    Deterministic graders — the ones that need no LLM
    
        
    Most assertions are cheap, fast and 100% repeatable: does the output match exactly, contain a string, match a regex, or parse as JSON? Each returns a {pass, score} — for binary graders the score is just 1 or 0. This is the exact grader the demo runs.
    
        
    // STEP 4 — deterministic graders → {pass, score}.
function grade(type, output, assertion) {
  const out = String(output);
  if (type === "exact_match") { const p = out.trim() === String(assertion).trim(); return { pass:p, score:p?1:0 }; }
  if (type === "contains")    { const p = out.toLowerCase().includes(String(assertion).toLowerCase()); return { pass:p, score:p?1:0 }; }
  if (type === "regex")       { let re; try { re = new RegExp(assertion); } catch { return { pass:false, score:0 }; } const p = re.test(out); return { pass:p, score:p?1:0 }; }
  if (type === "json_valid")  { try { JSON.parse(out); return { pass:true, score:1 }; } catch { return { pass:false, score:0 }; } }
  return rubric(out, assertion);   // ↓ step 5
}
    
      
    5. 
      
  5. 
        
    5
    A rubric grader — a graded score, not just pass/fail
    
        
    Some quality is partial. A rubric awards a fraction — here, how many required keywords the output hits — so avg score can separate two variants that have the same pass-rate. (In production this rubric is often an LLM-as-judge — that's Day 58 — but a keyword rubric is deterministic and testable.)
    
        
    // STEP 5 — rubric: fraction of required keywords present.
function rubric(output, assertion, threshold = 0.5) {
  const kws = String(assertion).split(",").map(s => s.trim()).filter(Boolean);
  if (!kws.length) return { pass: false, score: 0 };
  const hit = kws.filter(k => output.toLowerCase().includes(k.toLowerCase()));
  const score = hit.length / kws.length;          // 0..1  (partial credit)
  return { pass: score >= threshold, score };
}
    
      
    6. 
      
  6. 
        
    6
    Run the matrix — pass-rate + average score per variant
    
        
    The harness loop: for every variant, run the prompt on every test, grade the output, and reduce the column to a passRate (fraction of cells that pass) and an avgScore (mean cell score). In the demo the model call is a lookup into canned outputs; swap in a real generateText and nothing else changes.
    
        
    // STEP 6 — fill the matrix, reduce each column to stats.
async function runEval(variants, tests, callModel) {
  return Promise.all(variants.map(async (v) => {
    const cells = await Promise.all(tests.map(async (t) => {
      const output = await callModel(v.system, t.input);   // ← real LLM here
      return grade(t.grader, output, t.assertion);
    }));
    const passes = cells.filter(c => c.pass).length;
    return {
      id: v.id,
      passRate: passes / tests.length,
      avgScore: cells.reduce((a, c) => a + c.score, 0) / tests.length,
      cells,
    };
  }));
}
    
      
    7. 
      
  7. 
        
    7
    Pick the winner & gate on regressions
    
        
    The winner is the highest pass-rate, tie-broken by avg score. But shipping needs one more check: diff the candidate against the baseline cell-by-cell and block if any test went pass → fail — even when the overall pass-rate went up. This is the guardrail that turns an eval into a CI gate.
    
        
    // STEP 7 — winner by pass-rate; fail on ANY regression.
function pickWinner(rows) {
  return rows.slice().sort((a, b) =>
    b.passRate - a.passRate || b.avgScore - a.avgScore)[0];
}
function regressions(base, cand, tests) {
  return tests.filter((t, i) => base.cells[i].pass && !cand.cells[i].pass);
}
// in CI:
const dropped = regressions(baseRow, candRow, tests);
if (dropped.length) throw new Error(`${dropped.length} regression(s) — blocked`);
// ↑ V3 beats V2 on pass-rate but drops the thank-you test → CI catches it.

    📋
    Copy-paste — the same eval as a promptfoo config
    
        
    In practice you rarely hand-roll the harness — you write a promptfooconfig.yaml, list your prompts and providers, attach assertions to each test, and run npx promptfoo eval for the matrix (and promptfoo view for the web UI). The same graders live under assert.type; wire it into CI so a regression fails the build.
    
        
    # promptfooconfig.yaml  —  run:  npx promptfoo@latest eval
prompts:
  - "Classify this support email: {{input}}"                        # V1
  - "Classify. Return ONLY JSON {category,urgent}: {{input}}"       # V2
  - file://prompts/v3_fewshot.txt                                   # V3
providers:
  - anthropic:messages:claude-sonnet-4-5
  # (compare models side-by-side too — providers are columns as well)

defaultTest:
  assert:
    - type: is-json          # every output must parse as JSON

tests:
  - vars: { input: "How do I reset my password?" }
    assert:
      - type: contains
        value: account
  - vars: { input: "The whole site is down, nobody can log in!" }
    assert:
      - type: regex
        value: '"urgent"\s*:\s*true'
  - vars: { input: "Just wanted to say thanks!" }
    assert:
      - type: equals
        value: '{"category":"feedback","urgent":false}'
      # - type: llm-rubric        # ← Day 58: grade with a model
      #   value: "category is feedback and urgent is false"

# CI:  promptfoo eval --no-cache && promptfoo eval --output out.json
#      then fail the job if pass-rate drops vs the committed baseline.

🎉 Day 57 of PromptFromZero done.
You learned prompt evals: treat a prompt like code you can test. Pin a fixed test set (inputs + expected answers or assertions), write candidate variants, and grade every (variant × test) with deterministic graders — exact-match, contains, regex, JSON-valid and a rubric score — into a results matrix. Read the winner off the highest pass-rate (tie-broken by avg score, which captures partial quality a binary gate can't), keep a holdout so you don't overfit the prompt to the tests, and — the part that actually saves you — diff the candidate against a baseline so a change that lifts the average can't silently regress a case that used to pass. Run it locally with a tiny harness or from the CLI with promptfoo, and gate it in CI so quality can only go up. It's the discipline layer under everything in this series: every pattern from Days 1–56 becomes shippable once you can measure it. 👉 Next up — LLM-as-judge: when the “right answer” is fuzzy (tone, helpfulness, faithfulness), grade outputs with a model against a rubric instead of an exact string.
