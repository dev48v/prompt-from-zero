💾 Prefix caching — the provider caches your prompt by exact token-prefix match, so what you get back is the longest common prefix between this request and the cached one, and nothing after the first difference. Nothing here simulates language: the engine is an ordered list of segments with declared token lengths, a longest-common-prefix measured in tokens, and a stated price model — a cache write costs 1.25× a fresh input token, a cache read 0.10×. One field, seven places to put it

The system prompt is six stable segments. The volatile field goes in front of one of them, or after all of them. Nothing else changes — same tokens, same content, same order otherwise.

1. The hit length is a cumulative sum, and that is the whole mechanism

A prefix cache compares tokens from position zero and stops at the first one that differs. So the hit is not “most of the prompt minus the changed bit” — it is everything before the changed bit, and none of what follows, however stable that tail is. Put the volatile field at index p and the hit is exactly the cumulative token count of segments 0…p−1. The table below is measured by running the matcher, and the last column is that cumulative sum computed separately; they agree at every position.

Which makes the monotonicity assertion the real content of the page: moving the field one segment earlier can never increase the hit, and the engine checks that over every insertion point of a 48-segment prompt as well as this one, not over a few sampled slots.

2. Caching is a loan, and the break-even is closed-form

The first request pays 1.25× for the privilege of writing the entry. Every later one pays 0.10× for what it hits. So there is an N at which the discount has repaid the surcharge, and it is worth deriving rather than guessing. With hit H, cacheable prompt Ta, and the three multipliers w, r, b:

3. The threshold that does not depend on the prompt

Set that denominator to zero and the fixture drops out. What is left is a pure property of the price model: caching repays only if the hit is at least (w − b) / (w − r) of the cacheable prompt — 21.74% at the stated multipliers, whatever the prompt is made of. It is not approximately flat — hit length is independent of the volatile field's token count by construction, because the matcher stops at the first differing token and the field's own length is entirely on the far side of that stop. An 800-token volatile block at position 0 and a 1-token one cost the same hit: zero.

…and several volatile fields are only as bad as the earliest one

So the audit is not “how many volatile things are in my prompt”. It is “what is the earliest one” — everything after it is already free to change, and tidying those is worth exactly nothing.

What this measures and what it does not

Not this page: Day 71 — prompt caching covers cache breakpoints, TTL, minimum-prefix tiers and concurrency. All of those are held fixed here. This page varies exactly one thing — where the volatile field sits in the prefix — and prices the consequence.

Real: the prefix matcher, the cumulative arithmetic, the break-even algebra and its agreement with a request-by-request simulation, every count. Declared: the three price multipliers and the input dollar rate, so every multiple is a property of those numbers — and the one inequality worth stating separately is that a cache read is never dearer than fresh input of the same length under this model, which the engine asserts across the whole sweep rather than assuming. Not modelled, deliberately: cache lifetime and eviction, minimum cacheable prefix lengths, explicit breakpoints, concurrency, and the question of which prefix the provider actually keeps when several are live. Those are a different page's subject — this one holds them all fixed so the position of a single field is the only thing that moves. Also not this page: nothing here is about which instruction wins when two conflict. Segment order changes the bill; it is not an argument about precedence or authority, and no claim on this page depends on a model obeying anything.

How it works

// a prefix cache stops at the first differing token, so the hit is a running sum
function lcpTokens(a, b) {
  let t = 0;
  for (let i = 0; i < Math.min(a.length, b.length); i++) {
    if (a[i].sig !== b[i].sig || a[i].tokens !== b[i].tokens) break;
    t += a[i].tokens;
  }
  return t;
}

// and the bill for one served call is three terms and no branches
cost = H * PRICE.read + (Ta - H) * PRICE.write + Tb * PRICE.base;

A segment with zero tokens is never put into the stream at all, which is the only special case: an empty field is not in the token sequence, so it cannot break a prefix. That is also the identity the self-check uses — with the volatile field at zero tokens, every position must return the full hit.
