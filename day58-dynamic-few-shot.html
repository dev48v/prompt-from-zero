PromptFromZero · Day 58

🎯 Dynamic Few-Shot — instead of pasting the same static examples into every prompt (that's Day 4), you keep a pool of labeled exemplars and, for each incoming input, retrieve the k most similar ones and build the few-shot prompt on the fly. It's kNN in embedding space: embed every exemplar once, embed the query, score each exemplar by cosine similarity, take the top-k, and paste only those in front of the question. Why bother? A fixed example set is a compromise — it has to cover every kind of input at once, so for any particular input most of its examples are irrelevant noise, and the cases it happens not to cover get no help at all. Dynamic selection makes the examples relevant to this input: a billing question pulls billing exemplars, a cancellation question pulls cancellation exemplars — the model sees the pattern that actually matches what it's being asked, which lifts accuracy and lets a small k beat a big static block on both quality and tokens. This page is genuinely interactive with no API and no network: a self-contained JS demo with a 15-exemplar pool, a query box (type your own or pick a preset), a lightweight TF-IDF bag-of-words embedding that scores every exemplar against your query by cosine, a k slider, and the assembled dynamic prompt rendered live — with each pick's similarity score and shared terms — right next to a fixed static-few-shot prompt so you can watch dynamic surface more relevant exemplars per query. Everything is deterministic. Distinct from Day 4 (static few-shot — one fixed set for all) and a cousin of RAG (Day 5) — here we retrieve examples, not facts.

🔑 Static few-shot fixes the examples; dynamic few-shot fixes the pool and picks per input. A static block has to serve every possible input with one set of examples, so it's a permanent compromise: for any single query most of its examples are off-topic filler that spends tokens and dilutes the pattern, and any input whose kind it didn't anticipate gets no relevant demonstration at all. Dynamic few-shot flips that — you curate a broad pool once, embed it once, and at request time retrieve the k exemplars nearest the query in embedding space (kNN by cosine) and paste only those. The examples the model sees are now about the thing it's being asked, so a smaller k carries more signal than a bigger static block. Watch it here: on a cancellation query the static set — billing/shipping/technical/account — offers nothing on point, while the retriever surfaces the two cancellation exemplars at the top. The lightweight TF-IDF embedding matches on shared words (a real system swaps in dense embeddings that also catch synonyms), but the machinery is identical: embed once, score by cosine, take top-k, assemble on the fly.

Dynamic few-shot = a labeled exemplar pool + an embedding + cosine kNN → the k most similar examples, assembled into a per-input few-shot prompt. Relevant examples, small k, no wasted tokens.

🔨 Build it yourself

    
Dynamic few-shot is a tiny retriever glued to your prompt builder: a pool of labeled exemplars, an embedding (computed once), a cosine ranker, a top-k selector, and an assembler that pastes only the winners. Below is the exact deterministic harness the demo runs — plain, dependency-free functions you can lift straight into a project — followed by the production shape (real embeddings, precomputed and cached) and a copy-paste assembly template. Same idea both ways: embed once, score by cosine, take top-k, build the prompt on the fly.

    2
    The exemplar pool — labeled examples, curated once
    
        
    The pool is your knowledge base of demonstrations: input + the label/output you want the model to imitate. Curate for coverage (every category you expect), quality (correct, canonical labels — a wrong exemplar teaches the wrong thing), and no near-duplicates. This is the exact pool the demo ranks.
    
        
    // STEP 2 — the exemplar pool (input + gold label).
const POOL = [
  { text: "I was charged twice and need a refund.", label: "billing" },
  { text: "Where is my package? Delivery has not arrived.", label: "shipping" },
  { text: "The app crashes with an error every time.", label: "technical" },
  { text: "I forgot my password and cannot login.", label: "account" },
  { text: "Please cancel my subscription before it renews.", label: "cancellation" },
  { text: "This product is amazing, thank you!", label: "feedback" },
  // ...cover every category you expect at inference time
];

  3. 
        
    3
    Embed the text — a vector per exemplar (precompute)
    
        
    To measure similarity you need vectors. The demo uses a lightweight TF-IDF bag-of-words: tokenize, weight each term by how rare it is across the pool (rare words carry more signal), so each text becomes a sparse vector. Crucially, embed the pool once and store it — only the query is embedded per request.
    
        
    // STEP 3 — lightweight TF-IDF embedding (deterministic, no model).
function tokenize(t){ return (t.toLowerCase().match(/[a-z0-9]+/g)||[])
  .filter(w => w.length >= 2 && !STOP.has(w)); }

function buildIdf(docsTokens){                 // rarity weight per term
  const N = docsTokens.length, df = {};
  docsTokens.forEach(toks => new Set(toks).forEach(t => df[t]=(df[t]||0)+1));
  const idf = {};
  for (const t in df) idf[t] = Math.log((N+1)/(df[t]+1)) + 1;
  return idf;
}
function vectorize(tokens, idf, dflt){          // vec[term] = tf * idf
  const tf = {}, v = {};
  tokens.forEach(t => tf[t]=(tf[t]||0)+1);
  for (const t in tf) v[t] = tf[t] * (t in idf ? idf[t] : dflt);
  return v;
}
// PRECOMPUTE: const vectors = POOL.map(e => vectorize(tokenize(e.text), idf, dflt));
    
      
    4. 
      
  4. 
        
    4
    Cosine similarity — closeness, ignoring length
    
        
    Cosine measures the angle between two vectors, not their magnitude — so a short query and a longer exemplar can still score high if they point the same way (share the important terms). 1.0 = identical direction, 0 = no shared terms. This is the exact scorer the demo runs.
    
        
    // STEP 4 — cosine similarity between two sparse vectors.
function cosine(a, b){
  let dot = 0, na = 0, nb = 0;
  for (const k in a){ na += a[k]*a[k]; if (k in b) dot += a[k]*b[k]; }
  for (const k in b){ nb += b[k]*b[k]; }
  return (na && nb) ? dot / (Math.sqrt(na) * Math.sqrt(nb)) : 0;
}
    
      
    5. 
      
  5. 
        
    5
    kNN select — score all, sort, take the top-k
    
        
    The selection itself: embed the query, score it against every precomputed exemplar vector, sort by similarity, and keep the k highest. That's k-nearest-neighbours in embedding space — no training, just distance. Return the picks (and their scores) so the assembler and the UI can show why each was chosen.
    
        
    // STEP 5 — kNN: score every exemplar, take the k nearest.
function selectExemplars(query, pool, vectors, idf, dflt, k){
  const qv = vectorize(tokenize(query), idf, dflt);
  return pool
    .map((e, i) => ({ exemplar: e, sim: cosine(qv, vectors[i]) }))
    .sort((a, b) => b.sim - a.sim)      // nearest first
    .slice(0, k);                        // top-k
}
    
      
    6. 
      
  6. 
        
    6
    Assemble the prompt — paste only the selected exemplars
    
        
    Build the few-shot prompt from the picks: a task header, each selected exemplar as an input→label pair, then the query with the label left blank. This is what changes per request — same template, different (relevant) examples. This is the exact assembler the demo renders.
    
        
    // STEP 6 — assemble the few-shot prompt from the picks.
function assemblePrompt(picks, query){
  const header = "Classify the support message into exactly one label:\n" +
    "billing | shipping | technical | account | cancellation | feedback";
  const shots = picks
    .map(p => `Message: "${p.exemplar.text}"\nLabel: ${p.exemplar.label}`)
    .join("\n\n");
  return `${header}\n\nExamples:\n${shots}\n\nMessage: "${query}"\nLabel:`;
}

  7. 
        
    7
    Wire it up — the per-request pipeline (real embeddings)
    
        
    In production swap the TF-IDF stub for a real embedding model, but precompute the pool once (embeddings are cache-able and immutable) and, at scale, store them in a vector index so top-k is an ANN lookup, not a full scan. The request path is just: embed query → retrieve top-k → assemble → call the model.
    
        
    // STEP 7 — production pipeline (embed pool ONCE, retrieve per request).
import { embedMany, embed, generateText } from "ai";
import { openai } from "@ai-sdk/openai";

const emb = openai.embedding("text-embedding-3-small");
// ONCE at startup (or store in a vector DB — Pinecone/pgvector/etc.):
const { embeddings: poolVecs } = await embedMany({ model: emb, values: POOL.map(e => e.text) });

async function dynamicFewShot(query, k = 3){
  const { embedding: qv } = await embed({ model: emb, value: query });
  const picks = POOL
    .map((e, i) => ({ exemplar: e, sim: cosineSim(qv, poolVecs[i]) }))
    .sort((a, b) => b.sim - a.sim).slice(0, k);        // ANN index at scale
  const prompt = assemblePrompt(picks, query);
  const { text } = await generateText({ model: openai("gpt-4o-mini"), prompt });
  return { text, picks };                               // + which exemplars & scores
}

  8. 
        
    8
    Optional: MMR — trade a little relevance for diversity
    
        
    Pure top-k can return k near-duplicates — three ways of saying the same thing — wasting shots. Maximal Marginal Relevance re-ranks to keep picks that are relevant to the query and different from each other, so the k examples cover more of the input's facets. Tune λ: 1.0 = pure relevance, lower = more diverse.
    
        
    // STEP 8 — MMR: relevance to query MINUS redundancy with picks.
function mmr(qv, cands, k, lambda = 0.7){
  const picked = [];
  while (picked.length < k && cands.length){
    let best = null;
    for (const c of cands){
      const rel = cosine(qv, c.vec);
      const red = picked.length ? Math.max(...picked.map(p => cosine(c.vec, p.vec))) : 0;
      const score = lambda * rel - (1 - lambda) * red;    // penalise duplicates
      if (!best || score > best.score) best = { c, score };
    }
    picked.push(best.c);
    cands = cands.filter(x => x !== best.c);
  }
  return picked;
}

🎉 Day 58 of PromptFromZero done.
You learned dynamic few-shot: instead of one fixed example set for every input (static few-shot, Day 4), keep a curated pool of labeled exemplars, embed it once, and per request retrieve the k most similar to the input via cosine kNN — then assemble the prompt from only those. The examples become relevant to this input, so a small k carries more signal than a big static block and covers cases the fixed set never anticipated. You saw the whole pipeline live and deterministic: TF-IDF bag-of-words vectors, cosine scoring, a top-k slider, and the assembled prompt rebuilding as you type — with a static block beside it that can't adapt. In production swap the lightweight embedding for a dense model, precompute and cache the pool vectors, and use an ANN vector index so retrieval stays O(log n); mind the k tradeoff (too small is brittle, too big dilutes and burns tokens), consider MMR so your k picks aren't near-duplicates, and remember the pool is the model's knowledge — curate for coverage, correctness and dedup. It's the example-retrieval cousin of RAG (Day 5, which retrieves facts) and the adaptive upgrade of static few-shot (Day 4). 👉 Next up — LLM-as-judge: when the “right answer” is fuzzy (tone, helpfulness, faithfulness), grade outputs with a model against a rubric instead of an exact string.
