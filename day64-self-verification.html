PROMPTFROMZERO · DAY 64

🔁 Self-verification — asking a model to check its own answer sounds circular, and mostly is: "are you sure?" measures confidence, not correctness. What is not circular is backward verification — take the produced answer, substitute it back into the problem, mask one of the original givens, and ask the model to reconstruct that given. If the answer is wrong, the reconstruction usually disagrees with the number that was actually there, and the disagreement is a check anyone can run — including code, with no model in the loop. This page builds the whole apparatus over linear word problems: a generator that knows the ground truth, a solver that makes realistic mistakes at a rate you control, a real backward-substitution verifier, and then the part that matters — a confusion matrix showing that verification does not make things better for free. It costs one extra call per candidate, it rejects correct answers as well as wrong ones, and at some error rates the filtered output is worse than the unfiltered one. All computed live; the paper's accuracy figures are cited separately and never mixed in.

Every problem is generated with its answer known, so correctness is a fact rather than a judgement. The solver is a stand-in for a model: it solves correctly most of the time and makes plausible arithmetic slips otherwise.

"Are you sure?" is not a check


      
Ask a model to review its own answer and it will usually agree with itself, because the
      thing that produced the answer is the thing being asked to judge it, with the answer sitting
      right there in the context. You are measuring confidence, and confidence is
      not correlated with correctness in the way you need.


      
What breaks the circularity is changing the question, not the tone.


      

        
Backward verification

        
Substitute the produced answer back into the problem, mask one of the
        original numbers, and ask for that number. Compare the reconstruction against the value that
        was actually given.

      


      
Why this is different in kind

      
The forward task is "given a, b, c → find x". The backward task is "given x, b, c → find a",
      and a is already known. So the check does not need a judgement about quality; it needs
      an equality. That is why code can run it, and why it does not simply inherit the solver's
      original mistake.

      
The mechanism is closer to plugging your answer back in than to
      proofreading — the thing you were told to do in school, for exactly this reason.


      
It is not free, and this is the part that gets skipped

      

        
Verification throws away correct answers too. Every
        false-negative is a problem you could have answered and now refuse to. Papers report the
        accuracy gain; the amber cell of the confusion matrix is the price, and the RUN IT tab shows
        both together because reporting one without the other is how a technique gets oversold.

      


      
Precision, coverage, and the number people quote

      
After filtering you have two different numbers and they are easy to confuse:

      
    
        
  • Precision — of the answers you still give, what fraction are right.
    • 
        
  • Coverage — what fraction of problems you still answer at all.
    • 
      

      
A verifier that rejects almost everything reports magnificent precision. Quote precision
      alone and any filter looks like a breakthrough; you can reach 100% by answering one question.


      
Where it stops helping

      
The verifier has its own error rate. Once the solver is good enough, most of what the
      verifier rejects is correct, and filtering costs more accuracy than it recovers. Move
      the sliders and watch the green line meet the black one: past that point you are paying an
      extra call to make the output worse.

      
The same happens from the other direction. If the solver is very unreliable, the verifier is
      reconstructing from a wrong answer often enough that its own judgement degrades.


      
Verification composes with sampling

      
Generate k candidates, verify each, return the first that passes. That is where the
      technique earns its keep — it turns "one shot, hope" into "several shots, filtered", which is
      exactly self-consistency with a cheaper aggregator than majority voting. The slider shows the
      cost: k candidates means k+1 calls per problem, every time.


      
What this page is

      
A simulation of the pipeline, not of a model. The solver and the verifier are
      stand-ins with error rates you set, so every number here is arithmetic over known ground truth.
      Real measured accuracy for RCoT and similar methods belongs to the papers and is cited
      separately — mixing the two would make both meaningless.


    

  






  

    


      
🔨 Build it yourself


      
1. Generate problems whose answer you know

      
function makeProblem(rng){
  const rate  = 2 + Math.floor(rng() * 12);      // pens per box
  const boxes = 2 + Math.floor(rng() * 9);
  const extra = Math.floor(rng() * 20);
  return {
    text: `A box holds ${rate} pens. Priya buys ${boxes} boxes and is given ${extra} more. How many?`,
    givens: { rate, boxes, extra },
    answer: rate * boxes + extra
  };
}

      
Ground truth is not an opinion here, which is what makes every later number countable.


      
2. A solver that fails the way models fail

      
function solve(p, rng, errorRate){
  if (rng() >= errorRate) return p.answer;
  // realistic slips, not random noise
  const slips = [
    p.givens.rate * p.givens.boxes,                       // forgot the extra
    p.givens.rate + p.givens.boxes + p.givens.extra,      // added instead
    p.givens.rate * (p.givens.boxes + p.givens.extra),    // grouped wrongly
    p.answer + (rng() < 0.5 ? 1 : -1) * p.givens.rate     // off by one box
  ];
  return slips[Math.floor(rng() * slips.length)];
}

      
Random noise would be trivially detectable. Plausible-but-wrong is the case that matters.


      
3. Backward verification, as arithmetic

      
// Mask `boxes`. Given the candidate answer, reconstruct it and compare.
function verify(p, candidate, rng, verifierErrorRate){
  const reconstructed = (candidate - p.givens.extra) / p.givens.rate;
  let agrees = Number.isInteger(reconstructed)
            && reconstructed === p.givens.boxes;
  if (rng() < verifierErrorRate) agrees = !agrees;   // the verifier is fallible too
  return agrees;
}

      
Note the integer test. A wrong answer often reconstructs to a fraction, which is a stronger
      signal than a mismatch — the given was a count, so a non-integer is impossible, not merely
      different.


      
4. Report FOUR numbers, never one

      
let tp = 0, fp = 0, tn = 0, fn = 0;
for (const p of problems){
  const cand = solve(p, rng, errorRate);
  const correct = cand === p.answer;
  const passed  = verify(p, cand, rng, verifierErrorRate);
  if ( correct &&  passed) tp++;      // kept, and right
  if (!correct &&  passed) fp++;      // kept, and WRONG
  if ( correct && !passed) fn++;      // thrown away, and it was RIGHT
  if (!correct && !passed) tn++;      // correctly rejected
}
const precision = tp / (tp + fp);
const coverage  = (tp + fp) / problems.length;

      
Precision without coverage is the oldest way to make a filter look good. Print both or
      neither.


      
5. Sample k, verify each, take the first pass

      
function solveVerified(p, rng, k, errorRate, verifierErrorRate){
  for (let i = 0; i < k; i++){
    const cand = solve(p, rng, errorRate);
    if (verify(p, cand, rng, verifierErrorRate))
      return { answer: cand, calls: 2 * (i + 1) };
  }
  return { answer: null, calls: 2 * k };            // refused
}


      
6. Sweep, because a single setting proves nothing

      
Vary the solver's error rate and plot precision against unfiltered accuracy. The crossing
      point is the honest answer to "should I use this" — and it depends on your solver, not on the
      paper's.


      
7. Write the prompt so the check stays backward

      
Original problem, with one number replaced by X:
  "A box holds 7 pens. Priya buys X boxes and is given 4 more.
   She has 46 in total. What is X?"

Answer with a number only.

      
The forward answer must not appear as "the answer" anywhere in that prompt — it appears as a
      given. Leak the framing and you are back to asking "are you sure?".
