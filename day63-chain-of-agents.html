PROMPTFROMZERO · DAY 63

🔗 Chain-of-Agents (Zhang et al., 2024) — the long-context pattern that does not start by asking for a bigger context window. Split the document into chunks that each fit comfortably; give chunk 1 to a worker; hand its communication unit — a short running summary, not the text — to the worker reading chunk 2; repeat; then a manager answers from the final unit alone. The interesting question is not whether that works, it is what it costs and where it breaks, and both are computable without an LLM. This page implements the real chunker, a real token accountant, a needle-in-a-haystack harness that plants a fact at a known position, and three baselines to compare against — truncation, RAG-style top-k retrieval, and stuffing the whole thing in. It simulates the pipeline, never the model: every number below is arithmetic over real text, and the paper's accuracy figures are cited separately and never mixed into the live counters.

A fact is planted at the chosen position: "the archive key is —". The pipeline below is real: the chunker really splits, the token counter really counts, and the propagation really drops information when the communication unit runs out of budget.

Read it all, in pieces, without ever holding it all


      
There are only three honest answers to "the document does not fit".

      
    
        
  1. Truncate — read the first N tokens. Cheap, and wrong whenever the answer is not at the front.
    2. 
        
  2. Retrieve — embed, search, read the top-k chunks. Cheap and usually right, if the question is answerable from a few local passages.
    3. 
        
  3. Read everything — which is what Chain-of-Agents does, one window at a time.
    4. 
      


      
CoA is worth knowing precisely because of that third case. Retrieval is a filter, and a
      filter is exactly wrong for questions like "how many times does the narrator change their
      mind", "summarise the argument", "which clause contradicts clause 14" — questions whose answer
      is distributed. There is no top-k that contains it.


      

        
The pattern in one line

        
worker(chunk₁, ∅) → u₁ → worker(chunk₂, u₁) → u₂ → … → uₙ → manager(uₙ, question)

      


      
The communication unit is the whole design

      
Each worker passes forward a short unit — not the chunk, and not a generic summary. It is
      "what someone reading the rest of this document needs to know from my part, given the
      question". That conditioning matters: an unconditioned summary optimises for the wrong thing
      and drops the one number the question was about.


      

        
The unit is a fixed budget, and that is a lossy channel.
        Every hop is a chance to drop a detail. The chain view on the RUN IT tab colours each hop by
        whether the planted fact survived it — and with a small unit budget and many chunks, you can
        watch it disappear. Anyone who tells you CoA is lossless has not run the sweep.

      


      
What it costs

      
CoA reads more total tokens than stuffing, not fewer — every worker re-reads the
      instructions and the incoming unit on top of its chunk. What collapses is peak
      context: the largest single request. That is the number that decides whether the job
      runs at all on a given model, and it is why the pattern exists.

      
Both numbers are on the RUN IT tab, side by side, computed
      from the actual chunking rather than from a formula.


      
Sequential, and therefore slow

      
Worker i cannot start until worker i−1 finishes, because it needs
      ui−1. So latency is O(chunks) round-trips, where map-reduce over the same
      chunks is O(1) depth. That is the real trade: CoA keeps a thread of understanding
      across the document, and pays for it in wall-clock. If your question is genuinely per-chunk,
      map-reduce is both cheaper and faster, and you should use it.


      
What this page does not do

      
It does not call a model, and it does not pretend to. Every counter here is arithmetic over
      real text: real splitting, real token counting, real propagation with a real budget. The
      paper's reported accuracy gains over RAG and long-context baselines are a separate claim, made
      with real models on real datasets, and mixing them into these live numbers would make both
      meaningless.


    

  







  

    


      
🔨 Build it yourself

      
Build the accounting before the prompting. Every step below is checkable with no model in
      the loop, which means you can know what the pattern costs before you spend anything.


      
1. A token counter you control

      
You do not need a real BPE to make these decisions, but you do need to stop using
      "words × 1.3". Count something stable and state what it is.

      
// deliberately simple and DECLARED: ~4 chars per token, whitespace-aware.
function countTokens(s){
  if (!s) return 0;
  return Math.max(1, Math.ceil(s.length / 4));
}

      
State the assumption on screen. A number whose definition you cannot say out loud is not a
      measurement.


      
2. Chunk on boundaries, not on offsets

      
function chunk(text, budgetTokens){
  const sents = text.split(/(?<=[.!?])\s+/);
  const out = []; let cur = "", curT = 0;
  for (const s of sents){
    const t = countTokens(s);
    if (curT + t > budgetTokens && cur){ out.push(cur.trim()); cur = ""; curT = 0; }
    cur += s + " "; curT += t;
  }
  if (cur.trim()) out.push(cur.trim());
  return out;
}

      
Splitting mid-sentence is how the needle gets cut in half and neither worker reports it.


      
3. The worker, as a pure function over text

      
The real worker calls a model. The testable worker is the part around it: what goes
      in, what budget comes out, and what happens when the budget binds.

      
function worker(chunkText, incomingUnit, question, unitBudget){
  // a real implementation prompts a model here. What we can test without one is
  // the CHANNEL: carry forward what matters, under a hard budget.
  const carried = selectSalient(incomingUnit + " " + chunkText, question, unitBudget);
  return carried;                       // this is u_i
}


      
4. Make the loss visible, do not hide it

      
The instinct is to write the unit so nothing is ever dropped. That is not possible under a
      fixed budget, and pretending otherwise produces a demo that lies. Instead, measure it: plant a
      known fact and check whether it survives to the end.

      
const needle = "the archive key is " + key;
const doc = plant(haystack, needle, positionPercent);

let unit = "";
for (const c of chunk(doc, windowTokens)) unit = worker(c, unit, question, unitBudget);

const survived = unit.includes(key);    // no model needed to decide this


      
5. Build the baselines before you claim a win

      
const strategies = {
  stuff:    doc => doc,                                  // needs the whole window
  truncate: doc => head(doc, windowTokens),
  topk:     doc => retrieve(chunk(doc, windowTokens), question, k).join(" "),
  coa:      doc => runChain(doc)
};

      
Then report calls, total tokens, peak tokens and survival for each. The
      table on the RUN IT tab is exactly this, run live.


      
6. Sweep the position — one sample is not a result

      
Needle-in-a-haystack plots exist because performance depends heavily on where the
      fact is. Truncation looks perfect at 0% and fails everywhere else. Sweep every position and
      report the curve, not a single number.
